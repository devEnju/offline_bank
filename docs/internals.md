# Internals

For people changing the patches. Three parts: the [Bank](#bank) patch, the [storage](#storage) format both patches share, and the [Transporter](#transporter) patch. Addresses are ARM virtual addresses of the exact program versions named under each Scope; they come from static disassembly of the two programs and host tests.

## Bank

The patch for Pokémon Bank. What it does for a user is in [bank.md](bank.md).

### Scope

### Patches for Bank

A patch for Bank is a crate of its own with its own payload, its own profile in the builder, and its own package. It takes from `bank-common` what does not change what Bank does, and adds its hooks.

| | From `bank-common` and `patch-common` | The patch's own |
| --- | --- | --- |
| Loaded and executable | `patch-common`'s `bootstrap`, and the builder's start-up edits | |
| Bank's files | `fs` (access), `bank_files` and `session` (names, sizes, order of writes) | which of them it reads or writes, and when |
| Off the main thread | `patch-common`'s `worker`: thread, mailbox, staging buffer, collecting a job's reply; `bank-common`'s `program::Bank15` (Bank's SDK addresses) and `worker::WorkerError` | its jobs and what runs them (`worker::Service`) |
| On screen | `task` (task object, the router's answer, HOME and sleep through `patch-common`'s `home`, the screen with two numbers), `ui`, `fault` (the first number, the same in every patch for the same thing) | its hooks, and which tasks they replace |
| Hooks | `patch-common`'s `exclusive`: the state a patch's hooks share, one hook at a time; `message_stub!`, the entry's stub for the original's "show a message" | the state; the message entry, which asks the state whether a job is out |
| In the builder | `bank15.rs`: identity, placement, the shared edits | a profile: its table of edits, which names its entry functions |

**Rule: a patch writes Bank's files only through `bank-common`.** The byte formats exist once, in `offline-core`; the file names, their sizes and the order in which they are written exist once, in `bank-common`. A patch that writes a Bank has a PC test that loads the result with `BankFiles` and compares every byte. So what one patch writes, every other reads. The Transporter patch holds to it as well ([File access](#file-access-1)).

**Rule: a hook that is entered again while it runs does nothing.** The original's update of a task may call the task's busy poll, which a patch replaces with the same hook. Each patch's hooks share one guard; a task hook that finds it taken answers 0, "not done, next frame", and a router hook answers cleanup (`0x14`), as it does for a manager or task it cannot read. Transporter's router entry does the same with its disconnect step. A pointer a hook reads from an object of the original counts as one when it is not zero and word aligned (`patch_common::native::pointer`), in every patch. A function pointer it reads from one and calls must also lie inside that program's code (`native::code`, with the range `Program::TEXT`: Bank `00100000..00313910`, Transporter `00100000..0028D1AC`, each up to its start-up hook).

The **offline patch** is the rest of this part. The **migration patch** converts a Bank that an earlier release stored ([Files](#files)) and has none of the offline behaviour. START enters task 3, whose hooked update and busy poll run only the conversion on the worker; the native game scan and task 9 never run. It first probes the extdata archive without creating it: archive NotFound gives the existing "no Bank" result, while other errors stop the conversion. The conversion uses native preparation message `0x02`, including the power-off warning. Every result, including `0000600D 00000001` for a conversion, goes directly to the existing `Notice::done`: the localized HOME instruction, the label and two numbers stay until Bank is closed. The label names the earlier way it found and the release converting it, as "v0.2.1-1.2.3" or "v0.4.0-1.2.3"; without one (no Bank, already converted) it is the version and package, "v1.2.3-migration" (`migrate::label`, `Notice::relabel`). No success message, success sound or A press precedes it. Reopening and pressing START finds the converted Bank. The shared and separate edits are:

| --- | --- | --- |
| Start-up hook and its call (`001040a4`, `00313910`) | yes | yes |
| A corrupt extdata archive is kept (`0029f338`) | yes | yes |

Every entry function is a patch's own. `bank_message_stub` is each patch's own under one name, as its job is: it lets HOME and sleep through only when the patch has no job out ([HOME button and sleep](#home-button-and-sleep)). `bank_version_shown` is each patch's own under one name too: the start screen writes "Ver. 1.5" by putting two numbers into its message `0x4E` and calling `001e21c8(context, 0, 0x24, 0x4E)`, which loads the message into the first of the context's two work strings (`[context + 4]`), fills in the values into the second and hands that to the pane (`001e264c` finds it, `0029a628` sets its text). The entry makes that call, adds the patch's name to the second string in place and gives it to the pane again with the same two calls (`patch-common`'s `ui::version`, the same in Transporter). The line then reads "Ver. 1.5-offline", "Ver. 1.5-migration", or "Ver. 1.5-test" in a test build.

### The download patch

It lets the original run its online session and takes what the load put into the Bank object. The load is the one the original made for Pokémon HOME, which needs no game: none is chosen, read or saved. Its edits: the start-up hook and its call, the kept archive (`0029f338`), the router call (`002a5a2c`), the version line (`002b49c4`), task 3's update and busy poll (`00361ac4`, `00361ad4`, `bank_download_scan` / `bank_download_scan_busy`), task 9's update and busy poll (`00361cfc`, `00361d0c`), and the update of task `0xC` (`00361be4`). Ten regions, seven entry functions. It does not edit the first-start instruction words, the show-message function (the original refuses HOME and sleep for its whole online session itself), the load, the save, the reward claim, the clock or the main menu.

**The original's online session**, as its router (`002a5580`) orders the tasks:

| 4 | main menu | `0xA` for "Use Pokémon Bank" |
| `0xA`, `0xB` | game selection, scene | `0x11`, or `0x12` |

The original takes the second load only when its scan found no usable game and the user chose Pokémon HOME: the scan then ends with outcome `0x17`, the router sets the manager's byte `+0x1C` (`002a56b8`), and task 9 is followed by `0x1C` instead of the menu (`002a576c`). The load's set-up being the original's, the session has to be closed the original's way afterwards.

**What the patch changes** ([navigation.rs](../patches/bank-download/src/navigation.rs), tested against the transcription of the original router in [router.rs](../crates/bank-common/src/router.rs)):

- *Task 3 checks local data before its original update runs.* The worker probes the archive without creating it, then asks `BankFiles::open` whether an offline Bank is on the card. If one is, the result is `D0AD 2`, without contacting anything. Only archive NotFound or an empty/interrupted initialization permits continuing; other inspection errors stop the download, including previous-format file sizes.
- *Native setup runs without game detection.* With no local Bank, task 3 restarts at state 0 to prepare the archive, then the hook changes states `1..0x11` to `0x12`. This retains native first-start/save bookkeeping and prompts before connecting, while bypassing all cartridge and installed-game detection and the no-game HOME question. The native busy poll is preserved during this preparation. No scan availability byte decides whether the download proceeds.
- *After task 9 the load without a game follows*: where the original answers its menu, the router hook answers `0x1C`. The menu, the game selection and the checks of a game's last session are not entered.
- *After that load the reward step follows*, where the original would release the session (`0x1D`) and show its HOME screens (`0x1B`). The release is made after the files are written, by `0x13`, which sends the same request; `0x1D`'s end would also take the loading panel down before the write (`002affa4`).
- *Online, task 9 is the original's.* Both slots call the function they held. Before the original's first frame the update hook reads the reply byte above; with `0x35` it ends the task as failed, which the original answers with cleanup, and the result is `BAD 1`. The patch creates nothing on the server.
- *The reward step writes the files.* Task `0xC`'s set-up (`002ad77c`) only takes the shared UI and sends nothing, and it is the task the original enters after a load. Its update is the patch's: it copies the Bank object (`NativeBank::snapshot`, the range the original's save and restore use) into the worker's buffer, has the worker write it with `BankFiles::initialize` (the main file and the transport box first, the Bank file and the journal last), and ends with outcome `0x15`. The original router answers that with `0x13` by itself. The session is closed whether the files could be written or not.
- *After cleanup, task 9 runs again* if a result exists. Its set-up creates the shared UI that cleanup destroyed (`002aeb1c`). Every result uses `Notice::done`, including `0000D0AD 00000001` for a written Bank: the localized HOME instruction, build version/package label and numbers stay until Bank is closed, with no success message, success sound or A press. Stage `Decided` stays set through release, cleanup and this screen. Reopening and pressing START finds the Bank (`D0AD 2`).

Everything in the Bank object comes along: boxes, the transport box, the Pokédex part, and the Miles balance with its reward date, which are fields of the object. What only the server filled does not come along: `download::write` sets every unused place ([Native body](#native-body)) to what a new Bank has there, which includes the patch's two Miles fields, no remainder and never redeemed.

### Placement

The payload links at `003fb000`, after the original BSS. The paired exheader enlarges the data segment and sets BSS to zero (fields `0x34`, `0x38`, `0x3c` only); the IPS writes the former BSS, the payload, and its zero tail explicitly. Luma bounds IPS records by the allocated image, so `code.ips` and `exheader.bin` only work together. The start-up hook (`patch-common`, the same in every patch of both programs) duplicates the process handle (SVC `27`), sets the payload's code pages RX (SVC `70`), and flushes the caches whole (Luma SVC `92`/`94`). The range calls (`91`/`93`) are not used: the kernel carries a small range out by virtual address on every core, which faults where another process runs, and flushes everything only for a large one.

### Tasks and routing

Task object: vtable `+8` init, `+c` update, `+14` end, `+1c` busy poll; state at `+10`, outcome byte at `+30`. Factory `002a5a7c`, router `002a5580`. The factory makes tasks `0..0x1D` (`cmp r1, #0x1e` at `002a5a80`). Every hook that is given a task first checks that its vtable is one of the tasks it patches (`Task::from_raw`) and fails otherwise. The builder and the verifier hold the factory's bound, its cases for these tasks and their vtables' addresses (`0xD` through its constructor `002abb10`); the update slots are edits, which name their original words. The verifier also keeps the factory, that constructor and each vtable's first three words unchanged.

| ID | Task | ID | Task |
| --- | --- | --- | --- |
| 2 | Start screen | `0xC` / `0xD` | Reward guard / claim |
| 3 | Game scan | `0x19` | Box screen |
| 4 | Main menu (never created) | 7 | Save |
| 9 | Open Bank | `0x14` | Cleanup, then task 2 |
| `0xA` | Game selection | `0x10` | Load Bank |
| `0xB` | Scene set-up | | |

`navigation::destination` rewrites the original router's answer: `3 → 9`, `9 → 0xA` (original: 4), `0xA` outcome `0x13` → `0x14` (original: 4), `0xA` outcome 5 → `0xB` (as the original), `0xB → 0x10`, `0x10 → 0xC`, box-screen cancel → `0x14`, a cancelled task (the manager's flag `+0x1a`) → `0x14`, as the original answers it, and anything outside a small allow-list → `0x14`. HOME and sleep and the loading screen's time follow from that answer as from any other. A host test covers every input, with the original router's own answers: [router.rs](../crates/bank-common/src/router.rs) transcribes `002a5580` case by case from its jump table at `002a55ac`, for the tests of all three patches for Bank.

### The console test build

[building.md](building.md#test-builds-for-an-interrupted-save) says what it is for. It is the offline patch built with the feature `test-build`, and differs in five places:

- **The main menu is shown.** `navigation::destination` sends an opened Bank to task 4 and the menu's outcome `0xC` to game selection, as the original router does (`002a56d4`); every other outcome of the menu ends in cleanup. Back on game selection (outcome `0x13`) leads to task 4 again, as in the original. ### When a job cannot finish

A job that stops for a reason the original has a message for answers what it leaves (`storage_worker::Ending`) instead of failing ([storage_worker.rs](../patches/bank/src/storage_worker.rs)). A reply keeps the worker usable, so the next START works without closing Bank. The session ends at that message, which waits for A: `Step::TurnBack` in the opening and the load, `save_steps::Step::Stopped` in Save and Quit. The loading screen ends at once, as for an error. HOME and sleep are let through on the message, and once it is answered the task ends as failed, which the router answers with cleanup, then the start screen. The changes the session made in memory go with it; the next opening restores the Bank from its files. Every other failure shows the two numbers ([Screens](#screens)).

| `Ending` | What it leaves | The message |
| --- | --- | --- |
| `Retry` | A cartridge: its Game Card is gone, and nothing changed, or what is left is settled best by the next START with the game, whose selection then finds a save the write damaged ([Game saves](#game-saves)) | `0xB` from its second page (`ui::try_again`): "Please confirm that your Game Card is properly inserted, and then try again." |
| `NoSpace` | A file could not be made for lack of space, and nothing changed | Creating a Bank: the scan's own `0x26` (`ui::notice`), "Pokémon Bank could not be started due to a lack of space on your SD card." Save and Quit: the first line of message 0 of text file 26 (`ui::sd_full`), "The SD card is full." |

What counts:

- **A missing Game Card**, only for a cartridge, by the original's own test. Bank has no signal for a removed card: unlike Transporter (`001DE43C`, an event on notification `0x20A`), it never subscribes to that notification. Its game selection instead asks for the selected game's secure value (`00292D64` → `001643DC` → `00164370` → `0016578C`, FS command `0x0876`, slot `0x1000`) and shows message `0x1F` when the query fails. The worker makes the same query on the same archive (`query_fails`, through `platform`): a query that fails is a missing card, an answer that is not what the query gives is not. A call on the secure value that fails counts as a missing card too. Only a cartridge's card can be gone (`card_gone`): which kind of copy it is comes from the console's answer when the game is loaded, from the load in Save and Quit, and from the record of a save in progress (`transaction::bound`). An installed copy has no card to take out, and its failure is an error with its numbers. Loading asks the console first, before anything is read: a query that fails there is the original's missing card whatever the copy, as its game selection shows `0x1F` for it.
- **A card without room**: a read or write of Bank's files that the console failed (`bank_files::Error::card`) for lack of space, by the original's own test from its game scan (`patch_common::fs_result::lack_of_space`, `002abfa0`..`002abfd0`): a negative result of the file system module `0x11` with a description from `0xC8` to `0xDB`, for which the scan shows `0x26`. Any other refusal of the SD card is an error with its numbers, also with an installed game, which has no card to check: the advice about the Game Card does not help there, and a card that keeps refusing would otherwise never show what to report.

### HOME button and sleep

Bank keeps an activity mask in the byte at `00372988 + 2`; `001d4d90(bit)` sets a bit and `00229eb4(bit)` clears it. The main loop (`0010455c`) calls `0010ba04` every frame, which reports a change to the system, and the suspend callback `001050e0` refuses while the mask is not zero. A HOME press is accepted only while the mask is zero: `0010ba04` then sets the flag at `+1`, and the main loop calls the HOME handler `0010784c` once the current scene is ready (`00108634`), which can be several frames later. The handler does not look at the mask again.

- **Bit 1**: the original sets it for the whole online session and clears it in cleanup (`002abc7c`). The patch sets it in the routing hook whenever the next task is a loading task (`navigation::loads`: game scan, opening, scene set-up, loading, saving) and in `Runtime::submit`. It clears it in `Runtime::complete`, before the error dialog, before the "no game" notice and the message for a save that waits for its game, and in the routing hook for every other destination. Setting it per task, not per job, leaves no open frame between the scan and the opening. The panel of Bank loading stays into the reward step, the guard `0xC` and the claim `0xD` (`navigation::takes_panel`), which take it down: the guard in its state 0, the claim in its states 0 and `0x1b` or through the silent entry. A load that ends leaves the bit set (`Runtime::end_task`, not `complete`): the manager runs its end callback (`002afdd8`) on the next frames and only then the router. While the ended task leaves the panel on screen (`ui::loading_shown`: bit 0 of byte `+0xb7` of pane `0x97`, which `001e7084` sets and clears), the routing hook keeps the bit set; the reward hook clears it in the frame the panel is down, whatever the reward step shows next.
- **A message that waits** ends the refusal as well. The original's "show a message" function `001d6650(ui, kind, message, wait)` begins with `push {r4-r8, lr}`; that instruction is a branch to `bank_message_stub` (each patch's `hooks`, through `patch-common`'s `message_stub!`), which runs it, clears bit 1 if `wait` is not 0 and no job is out, and goes on at `001d6654` with every register as it came. The original shows such a message inside a loading task where it has nothing left to do but end: in the game scan, message `0x26` when the extdata cannot be created for lack of space (`002abfec`; the scan then waits for it in state `0x19` and ends as failed). No code of a patch runs there otherwise. Texts shown with `wait` 0 are loading texts and leave the bit as it is.
- **Accepted presses**: because the handler ignores the mask, a press accepted just before the mask was set would still be carried out. Accepting does nothing but set the flag at `+1` (`0010ba7c`; the handlers clear it afterwards at `00107924` and `00107a50`, and no other store to it was found), so the patch takes the press back: whenever it sets bit 1 it also clears that flag (`task::refuse_home`, through `patch-common`'s `home::refuse`, the same in Transporter). From that frame on the original refuses every press itself. The HOME Menu, and closing Bank from it, therefore never meet a loading screen or a running job, and nothing waits for a press to be carried out. A press on the very frame a loading screen begins is ignored like any press during loading. This is the one byte of the original's HOME state the patch writes.
- **Bit 4**: set by the game-save writer launch (also in the patch's launcher in [native_game.rs](../patches/bank/src/native_game.rs)) and cleared by the original when the writer finishes.

The busy flag from `0025c420` is unrelated: it protects a task from Bank's own cancellation, not from HOME.

### Worker thread

One native SDK thread (`002320d4`, trampoline `001211e4`, event `00235c6c`/`00234a00`/`00231e70`) owns all storage handles. The thread and its mailbox are `patch-common`'s, with Bank's addresses from `bank-common` (`program::Bank15`); what it runs is the patch's own (`worker::Service`, in the offline patch the jobs of [storage_worker.rs](../patches/bank/src/storage_worker.rs)). The main thread owns every native UI, task, and game object. The one exception is the game Save and Quit prepared: during `Job::Prepare` the worker reads its frozen blocks and makes the original's check of it, while the main thread leaves it alone. A single mailbox with atomic states passes fixed-size jobs and the staging buffer; neither thread ever waits on the other. Task hooks submit a job and poll once per frame, with native busy protection (`0025c420`/`0025c3e8`) keeping the task alive. The SDK argument is `0x11`: its wrapper adds `0x20` for ordinary priorities, producing kernel priority `0x31`, one below the main thread (`0x30`), on the same core. Passing kernel `0x31` as an SDK argument instead produces an invalid kernel priority and fails thread creation with `E0E01BFD`. The builder and independent verifier check the native conversion instructions. The worker runs while the main thread waits for the next frame. Stack 32 KiB with a guard pattern.

What the main thread has to do behind a loading screen takes one heavy native step per frame, as the original's task states do, so the screen keeps moving:

| Loading screen | Frame by frame on the main thread |
| --- | --- |
| Creating a Bank | the defaults (task 9 state 6); the body staged and `Job::Initialize` handed over (state 7) ([First start](#first-start)) |
| Opening (`Job::Open`, `Job::Recover`) | the body restored into the live Bank; its Pokédex views reloaded and checked, and loading ended |
| Loading the chosen game (`Job::LoadGame`) | the trainer read (`dex::trainer`); the game's Pokémon counted; the Bank's counted and the Miles begun |
| Save and Quit | `Job::Detect` handed over; the game's Pokémon counted; the Bank's counted, the Miles settled and the counts recorded; the game prepared; the Pokédex refreshed; the Bank staged and `Job::Prepare` handed over (`save_steps`) |

What stays on one frame is one call of the original that cannot be cut: rotate and prepare, a Pokédex reload, a count, the copy of the body. The original's own states behind its panels (the game scan, game selection) run as they always did. Between two of these frames only the patch's hook runs for the task: the original's update and busy poll of tasks 9, `0x10` and 7 are replaced, so nothing reads the Bank's Pokédex views between its restore and their reload.

Every patch submits and asks through `patch_common::worker::Requests`, which starts the worker on first use and keeps a job with the task that submitted it (`Pending`); its reply goes to that task only. Polled by another task, the job is waited for and its reply dropped, and only then does that task fail: what the job holds stays lent until it has ended. The thread is started with the first storage job and waits for jobs until Bank is closed; no job ends it. Between two jobs nothing of the Bank is open: after every job, also one that failed, the worker lets the Bank container rest (`BankFiles::rest`), which flushes and closes its open unit file and closes its archive handle (the smaller containers are never held open). What the session read of the journal stays for its next job, which opens the archive and the file it needs again. Every screen that waits for the user, the start screen and the error screen among them, therefore finds nothing open when HOME is pressed or Bank is closed from the HOME Menu; with a game started before Bank and not closed first, the HOME Menu stops with an exception while Bank holds its archive open. A session ends without a job of its own: every session ends in the cleanup task `0x14`, which runs as the original, and the next START's `Job::Open` opens the Bank as a first one does, dropping what the session before read. Letting go writes nothing: a save has made its writes durable before it ends, and a unit is flushed before it is closed. A session that ends in an error never gets to cleanup, since its screen stays; `Runtime::report_failure` waits for a job that is still out before that screen lets HOME through, with the loading screen up and HOME refused until then. A job that fails leaves the worker refusing every later job until Bank is closed; a job that cannot finish for a reason the original has a message for is a reply, not a failure ([When a job cannot finish](#when-a-job-cannot-finish)).

The games' saves are another matter: the original leaves every found game's save mounted until the next scan (`001D5344` unmounts and mounts; nothing unmounts at cleanup), and the patch reads `main` through those mounts.

### Loading screens

Every loading screen stands for 0.5 s before its work begins: it slides in while nothing is read, written or built behind it. A screen whose work succeeds stays at least 1.5 s; an error ends it as soon as it is found, which is never before 0.5 s ([spinner.rs](../crates/patch-common/src/spinner.rs)). The time is the original's clock, read every frame as its own minimum time `001d5bb0` reads it: `00229dc4` copies the time the main loop keeps at `00372fe0`, `002c8ea4` gives it in ms. The time is taken where the patch starts its panel. For a task whose set-up starts one (`navigation::spins`: the scene set-up `0xB`, saving 7, cleanup `0x14`), the routing entry only marks it as coming (`Spinner::coming`): the manager runs the set-up on a later frame, the scene set-up again on every frame until the old text window is closed (`001d6a34`). The time is then taken on the first frame of the patch behind the panel (`Spinner::seen`: loading's and saving's first update; cleanup runs no patch behind its panel), one to three frames after the panel went up, so a wait is never shorter than it is to be; until then everything waits.

| Loading screen | Goes up | Its work waits | A success ends it no earlier than |
| --- | --- | --- | --- |
| START: the scan, then the opening | in the scan entry ([Screens](#screens)) | in the scan entry, before the original's first state and its mount (`panel::Frame::Wait`) | the scan's own 1.5 s, which its end (`002acab8`) counts from its set-up; the opening follows |
| Creating a Bank | in task 9 state 4 | in state 6, before the defaults | `Step::Done`, before game selection |
| Loading the chosen game | in the scene set-up (`002af1c8`); it stays through task `0x10` into the reward step | in task `0x10`'s first step, before `Job::LoadGame` | `Step::Done`, before the reward step |
| Save and Quit | in task 7's set-up (`002b2540`) | in its first step, before `Job::Detect` | `save_steps::Step::Saved`, before the success message |
| Cleanup | in its set-up (`002abd6c`) | nothing: the original's own work comes after its 1.5 s | its own 1.5 s (`002abc7c`) |
| Migration | in the scan hook's first frame | in the scan hook, before the conversion | the result `600D`; any other at once |
| Download: the look at the card | in task 3's first frame | in task 3, before `Job::Look` | the result `D0AD 2` |
| Download: the result after cleanup | in task 9's first frame | nothing to do | the result `D0AD 1` |

What ends a screen early is an error: every error screen (`Runtime::report_failure`), a mount that fails, no usable game, a save in progress that waits for its game, every job that cannot finish ([When a job cannot finish](#when-a-job-cannot-finish)), and every result of the migration or the download but the ones above. The welcome comes after the scan's 1.5 s. The download's write at the reward step runs behind the panel of the original's load, which has stood through the server's load.

### Game saves

Save manager (0x100 bytes): selected kind at `+c8`; per kind `k` (1..8 = X, Y, OR, AS, S, M, US, UM), byte `k*12` is the kind, byte `+1` is "loaded", word `+4` the game object, word `+8` its writer. Game object: 0xb49d0 bytes, vtable `00362f88`, metadata pointer `+4`, kind byte `+8`.

- **Prepare** `002bc4bc` regenerates checksums (and Gen 7 signatures) after rotating the secure-value pair (`002bc7c4`). Both run on the main thread, as in the original (`0015dcf4` → `002bba8c`). Hash only after it.
- **Check** `002cbea0(game, detail)` recomputes every block's checksum and, in Sun to Ultra Moon, checks the signature; 1 is valid, 0 a metadata block that is all empty, 2 a damaged save. The original's writer thread makes it after the write (mode 4, `001d38d8`); its load does not (mode 1, and mode 2 passes 0 to `001d38d8` at `002bb120`), so the original loads a damaged save and its next save writes the mixed blocks with new checksums. The patch makes it of the chosen game on the main thread before the game is loaded (`NativeGameSession::check_loaded`), once its loading screen has stood for 0.5 s: a save that fails is not loaded, and the session ends at the original's message 2 of text file 23 (`ui::save_corrupted`, [When a job cannot finish](#when-a-job-cannot-finish)), "The saved data in your Pokémon game is corrupted.", through `Step::TurnBack`. Only that game is refused; a save in progress was settled by the opening before the selection. The worker makes it first in `Job::Prepare`, before it reads the game or writes anything, so a game that fails it is refused with nothing written (fault `C`). The main thread leaves the game alone until the job ends. For the signature the check overwrites 0x80 bytes of block `0x24` and restores them, and it takes the SDK's critical section (`00235658`) around a shared crypto state, as on the writer thread; it makes no file system or UI call and needs less than 2 KiB of stack.
- **Blocks** `002bc460(game, i)`: 55/58/37/39 data blocks (XY/ORAS/SM/USUM) plus a 0x1e8-byte metadata block, each written at a 512-aligned offset. Gaps and the file tail are not rewritten, so the expected after-image keeps their old bytes.
- **Write** uses the original writer thread (`001d37ec`, mode 4) and completion `0015dc74`, launched only after the journal is durable.
- **Secure value** slot `0x1000`. The platform value is advanced only by the one step a completed save takes, from the game file's own previous value to its current one: by a recovery whose journal matches the complete after-image, and by a load, for a save in progress that was settled without its game ([below](#an-interrupted-save)). Any other difference is fault `E`.

### Rewards

- Count: `001d5ec0(bank + 0xbb520)`, 100 boxes × 30 slots. Balance: `001d588c` / `001d59fc` on `bank + 0xbb528`.
- Native accrual in guard state 0 and claim state `0x1b` is `count × (1/30) × hours × (1/24)`. The hook sets the stored reward date to the session date first, so native accrual is zero; the patch's own accounting has put the earnings into the balance when task `0x10` finished.
- **Accounting** ([rewards.rs](../crates/offline-core/src/rewards.rs)) is the same step with the remainder kept, on the same fields. 720 Pokémon-hours are one Mile. When task `0x10` finishes, `begin_rewards` takes the reward date (`bank + 0x168`, six bytes: u16 year, month, day, hour, minute; `001d5880` points at it), the balance and the count from the restored object and adds `count × clock hours` since that date to the remainder kept in the object; the whole Miles go into the balance (`rewards::enter`). At Save and Quit `settle_rewards` adds the hours since the load at the count of the load and writes the balance and the date into the object before it is staged (`rewards::settle`); the remainder and the day of a redemption go into their two places in the object ([The Miles state in the body](#the-miles-state-in-the-body)). Clock hours are the full hours crossed between two moments, so no part of an hour is dropped at a save. The date written is the later of the stored one and now, and the redeemed day the later of the stored one and today: neither goes back. An object without a valid date earns nothing until its first save.
- The claim hook starts task `0xD` at state `0x1b` with `+4c = 1`, `+50 = 0`, and session `+38 = -1`, which skips service queries and distributions. Allowed states: `0`, `7..0xd`, `0x16`, `0x1b..0x22`, and for the welcome gift (below) `5` while it is due and `4`, `6` once it was given.
- The allowed states are a guard, not a path a user can reach. From `0x1b` with `+4c = 1` and session `+38 = -1`, the claim task goes to `0x22` (total 0) or `0x16`, then through `7`..`0xd`, `0x1c`, `0x1e`..`0x22`; state `0xa` becomes `0xb` in the choice listener `002d144c`. States outside the list are set only by the server-reply listener `002ab17c`, by the dialog listener `002d0c4c` from state `0x1a`, by the branches of states `0` and `0x1b` that those two fields rule out, and by the welcome's states 0, 5 and 4, while it is due. The guard task has eight states, all allowed.
- **Welcome gift.** The original's state 0 reads the flag at object `+0x180` (body `+0x178`; getter `002ba590`, setter `002ba59c`) and, while it is 0, sets it and shows message 4 (`002a9878`), then state 5. State 5 (`002a9bdc`), once message 4 is answered, sets `+50 = 100` and the balance **to** 100 (`001d59fc`), formats message 9 with `+50` and goes to state 4. State 4 shows message 8, state 6 the choice `0xA`, then state 7, the redemption states above. While the loaded Bank's flag is 0 (`RewardSession::welcome`; never in the test build), the hook lets state 0 run instead of starting at `0x1b`, and the guard checks as before an offer. Around state 5 the hook keeps the balance it found and, once the state moved on, sets it to that balance plus 100, up to 65,535 (`rewards::welcome`); message 9 says 100 also in the rare case that less fits. Before state 6 it writes the whole balance to `+50`, which the ordinary way's state `0x15` would have done, so the choice quotes it and the redemption is checked as any other. The flag is in the main file and set in memory only; it is written at Save and Quit, with the balance. A guard notice that the user goes past leads to the boxes without state 0, so the flag stays 0 and the welcome comes at a later opening. States 1 to 3, the server's gifts, stay refused.
- What is said (`rewards::dialog`, from the redeemed day, the day of the reward date as loaded, and the balance): nothing without a balance or after a redemption today; an offer for 10 or more; for 1 to 9 the message, unless the last save was today. For nothing, the hook sets the claim to state `0x22` (`002ab124`, the original's end for a total of 0), after ending the loading panel as the original's state `0x1b` does before it looks at the total (`002aac80`). The guard goes to state 4 (`002ad658`, outcome 5, no notice 7 / `0x51` about a present in the game or a full gift list) unless there is an offer: its notices stand in the way of a redemption only. Otherwise claim state `0x1b` shows message `0xE` for any total above 0 and state `0x16` message `0xF` below 10 or the choice `0x10` from 10 on. A verified redemption (below) sets the redeemed day at the next save.
- Redemption runs in state `0xb` (choice at `+60`, quote at `+50`) and ends in `0xc`. Gen 6 writes the gift buffer from `(*(game + 0x1c384))->vtable[2]`: flag `+1ff |= 0x80`, Miles at `+6a2`, BP at `+6a0`. Gen 7 inserts a 0x108-byte record (type 3 at `+51`, amount at `+68`) through `002b6d68` into the 48-slot store at `game + 0xad43c`; the original ignores that call's result, so the hook compares counts and the new record. `002b6d68` counts the used slots (a nonzero title halfword, as `001d58b0` does) and copies the record to the slot of that number (`002b7130`..`002b7140`), so the hook reads the new record at the count it took before the claim, the same slot the original writes.

### Pokédex

The records screen is the original's; nothing of it is edited. Its task (init `0026de9c`, update `0026d8ec`) is the only place where the original takes a game's Pokédex and records into the Bank: `002b8e00` stores the trainer's identity, `001e1ba8` copies nine record words, `001e1b94` copies the game's Pokédex into its version region and marks it valid, and no other function calls these three.

| The records screen is opened and the game's version slot | Import |
| --- | --- |
| is empty (`001e1e58` answers 0) | At once, in state 0: identity, records, Pokédex |
| belongs to the same trainer (`002cb7b8`) | At once, in state 0: records, Pokédex |
| belongs to another trainer | None. Choosing that game's row (state 4) shows the replacement question; Yes is state 6, which imports all three, No is state 7 |

State 0 imports only while the byte its caller passes is 0 (`[[task + 0x18]]`); the box screen's value was not traced. The import changes the Bank body in memory. The next Save and Quit stores it; without one it is gone, because the next opening restores the body from the files.

**A save refreshes a slot that is this trainer's already** (`dex::refresh`, the one thing here that is the patch's own). At Save and Quit, on the frame after the game's preparation and before the Bank is staged, the hook has `0026de9c` collect the selected game's data as the records screen does, asks the original's two questions about its version slot, and for the second row of the table makes that row's two calls, `001e1ba8` and `001e1b94`. An empty slot and another trainer's are left to the records screen. The import copies; it does not merge. It changes the body in memory before it is staged, so a save that is undone leaves the slot as it was. If the game cannot be asked, nothing is taken and the save goes on; if the import changed any other version's region (a digest of the eight before and after), the save stops with fault `2`.

What the patch does here beside that ([dex.rs](../patches/bank/src/dex.rs)): after every body restore it reloads the eight version caches, which lie outside the body, and has the totals built anew (`002b9a3c`, `002b9b90`); it reads the selected game's trainer through `0026de9c` for the record of a save in progress (`dex::trainer`), which reloads those caches itself (`002b9a3c`); and after a restore it checks, by a digest of the eight version regions, that reloading the caches left them as restored (`dex::evidence`). Nothing is restored after a save: the session ends in cleanup, and the live object is the body that was saved.

## Storage

The files of the offline Bank and the rules by which Transporter delivers into them. Both patches use the same code for this: [`offline-core`](../crates/offline-core/src/). The user-level description is in [bank.md](bank.md#where-the-bank-is-stored).

The Bank object of the original is `0xBB530` bytes; its serialized body is `object + 8`, length `0xBB518`. Only that range is stored; helper pointers behind it are never persisted. Offsets are hexadecimal.

A downloaded or converted Bank gets them the same way (`native_blob::clear_unused`); the conversion then puts its remainder back.

Pokémon records are encrypted with the LCG `seed * 0x41C64E6D + 0x6073`; the checksum at `+6` is the 16-bit sum of the 112 decrypted words.

### Files

All files are in SD extdata archive `0x00000C9B` (created by the original with room for 10 directories and 100 files). The body is cut at fixed offsets by what the data is, and each piece is stored unchanged, in body order ([sections.rs](../crates/offline-core/src/sections.rs)): the Bank file holds the Pokémon of the 100 boxes and what is kept per box slot, the transport box file the transport box, and the main file everything else Bank needs. Every byte of the body is in exactly one of them, and a file holds its ranges and nothing else: no header, no label, no padding.

| File | Length | Body ranges |
| --- | --- | --- |
| Bank | 729,800 | `17C..AAF14` (the boxes), `ACA44..AD5FC` (format tags), `B4AA0..BB418` (per-slot bytes and timestamps) |
| Main | 30,466 | `0..17C` (header), `AD61A..B4AA0` (padding, records, Pokédex, transfer counters), `BB418..BB518` (tail) |
| Transport box | 6,990 | `AAF14..ACA44` then `AD5FC..AD61A` |

The three lengths add up to the body's `BB518`. Each file exists in two copies. What ties a copy to a save is [the journal](#the-journal): one record of 140 bytes, kept twice.

**Every copy and every record is a file of its own** ([bank_files.rs](../crates/bank-common/src/bank_files.rs), `FileName::units`; the names are in [files.rs](../crates/offline-core/src/files.rs), which Transporter uses too). The code addresses them as three containers, each a range of fixed layout:

| Container | Length | Files, in the order of the layout |
| --- | --- | --- |
| Bank | 1,459,880 | `/journal.bin`, `/journal.alt.bin` (140 each): journal record A, B |
| | | `/bank.bin`, `/bank.alt.bin` (729,800 each): copy A, B of the Bank file |
| Main | 60,932 | `/main.bin`, `/main.alt.bin` (30,466 each): copy A, B |
| Transport box | 13,980 | `/mover.bin`, `/mover.alt.bin` (6,990 each): copy A, B |

The reason is how the console writes extdata. Each file is its own container with check values over blocks of its contents; new data is written in place before the check values are updated. A write that the power interrupts leaves the blocks it touched failing their check: reads return a result of the corrupted-data class (`D900458B` was seen), not bad bytes. Units that share a file share blocks at their edges, so in one file a write to the spare copy could take the copy in use with it, and did. With one file per unit, only the unit being written can be lost, and by the order of a save that unit never holds anything still needed.

`Split` in [fs.rs](../crates/bank-common/src/fs.rs) presents the unit files of a container as one range to the store and the pairs:

| A unit file that is | Reads | Writes |
| --- | --- | --- |
| there | as stored; an error if the console refuses | as written |
| absent | as zeros | are preceded by creating it, zero-filled |
| there but not to be opened | an error | an error |
| there with another size | the container does not open: a hard error, and it is never replaced | |

- A container counts as missing only when none of its files exists.
- A container that was closed answers every read, write and sync with an error; an absent unit reads as zeros only while the container is open.
- **One archive handle and one open file per container.** A container opens its archive once and has at most one unit file open, the one being read or written; one that rests (`rest`) holds neither and opens them again at its next read or write; opening a container only looks at each unit file (there, right size, opens) and closes it again. Leaving a unit flushes it first if it holds writes, so nothing depends on a write staying unflushed, and a flush that fails then is reported by that operation and by the next `sync`. The reason is a limit of the console: with every unit file open under an archive handle of its own, two containers of four units came to eight files and eight archive handles, and creating a file failed with an out-of-resource result (`D860466C`); five and five had worked. Which of the two ran out is not known. Bank holds its Bank container and one other at a time, the migration one source and one destination: two and two, what a Bank of one file per container used. The PC tests count it: the file layer's simulated card counts archive handles and files, the Bank tests' and the migration's count open containers and allow two. Transporter reaches the journal records and the transport box with calls of its own and holds one of the two pairs at a time ([File access](#file-access-1)); the tests count that too.
- `Storage::recreate` deletes one unit file, which leaves it absent. The store and the pairs ask for it when writing, syncing or reading back a unit fails, and then write once more; they only ever write units that are not in use.
- An unreadable journal record counts as a damaged one, and the other decides. A copy that cannot be read is an error where the record names it for the current save; the one exception is the transport box ([Saving and loading](#saving-and-loading)). Transporter replaces no file: one it would write and cannot read makes it refuse until Bank's next save has written it anew.

File names in 3DS extdata are limited to 16 characters without the leading slash; a longer name fails at creation with `E0E046C7`. `UnitFile::new` refuses longer names at compile time.

**The version of the stored files** is `offline-core`'s own version in its `Cargo.toml`, not a release's. Its major number is the journal version every record carries in byte 3 (`SCHEMA_VERSION`, computed from it): today 1.0.0, journal version 1. It changes only with the stored files, and then to the next whole number.

**Rule for new features:** never change the size, layout or meaning of an existing file or field. The three data files are the native body, and the record names exactly these three. Data that is not in the body needs a pair of files of its own and a place in the record. Any such change, and any change of what stored bytes mean (as v0.3.1 did to the binding of a save in progress and v0.4.0 to the Miles record, both without one), is a new version of the stored files: `offline-core`'s version goes to the next whole number, and the migration patch gets a folder for the files until then ([building.md](building.md#the-migration-from-earlier-releases)). Within one version every later release reads and settles everything an earlier release of it wrote; that is the current format, not legacy code. Two tests hold it: `bank_files::tests::the_files_are_those_of_this_journal_version` pins the names and lengths of the files, and `offline-core/tests/journal.rs` with `transaction::tests::every_save_in_progress_a_release_of_this_journal_version_recorded_binds` read the records of every release of this version (at rest, a waiting delivery, a save in progress), taken from its tag.

**The Bank of an earlier release** is stored in one of two other ways, each named for the last release that stored it so ([source.rs](../patches/bank-migrate/src/source.rs)):

| Way | Releases | Files | Rewards record, 16 bytes |
| --- | --- | --- | --- |
| v0.2.1 | up to v0.2.1 | Four, one per container: `/bank.bin` (both journal records and both snapshots), `/dex.bin`, `/transport.bin`, `/rewards.bin` | u32 balance at 0, with zero in the body; state at 4; thirtieths at 5; count at 6; the day accounted through at 8 |
| v0.4.0 | v0.3.0 to v0.4.0 | Ten: the same containers, each unit a file of its own (`/journal.bin`, `/journal.alt.bin`, `/bank.bin`, `/bank.alt.bin`, `/dex.bin`, `/dex.alt.bin`, `/mover.bin`, `/mover.alt.bin`, `/rewards.bin`, `/rewards.alt.bin`) | Remainder in Pokémon-hours as a u16 at 4, day of the last redemption at 8; at 0 the balance as v0.3.1 kept it there |

The offline patch reads neither. The migration patch converts either straight into the current files ([migrate.rs](../patches/bank-migrate/src/migrate.rs), [building.md](building.md#the-migration-from-earlier-releases)); nothing is written in an earlier way. It holds v0.4.0's storage code as a frozen copy ([v0_4_0/](../patches/bank-migrate/src/v0_4_0/)) and reads both ways with it, read-only: v0.2.1's containers are v0.4.0's byte for byte, and each is opened as the one file it is there ([v0_2_1/](../patches/bank-migrate/src/v0_2_1/)). A test pins the four lengths to v0.2.1's own. A folder hands the target ([target.rs](../patches/bank-migrate/src/target.rs)) only the native body and the Miles as the current release keeps them (`target::Miles`). Only the rewards record is read with the meaning its release gave it:

| Way | What goes into the body |
| --- | --- |
| v0.2.1 | The record's balance. Its thirtieths × 24 as the remainder in Pokémon-hours. As the reward date the day it is accounted through, 00:00: v0.2.1 paid `count × days / 30` up to that day, so hours are counted on from there and none is paid twice. A Bank without a record (never saved), or with one v0.2.1 does not read, gets no balance and no date and earns nothing until its first save, as in v0.2.1. |
| v0.4.0 | The body's balance, plus one in the record's first four bytes as v0.3.1 kept it there (`v0_4_0::rewards::balance_beside`). The record's remainder. The body's date. A Bank of v0.3.x is in these files and is read as v0.4.0 reads one. |

For both, the day of a redemption is not kept, and the unused places are those of a new Bank (`native_blob::clear_unused`). A Bank of v0.2.1 is known by its `/bank.bin` of v0.2.1's length, `00164C54`, which is also what the offline patch shows behind error 3 for it ([`fs`](../crates/bank-common/src/fs.rs) stops at the first file of another size); a Bank of v0.4.0 by a journal record of its length. Files of both at once are no Bank either release wrote and are left as they are (`00000BA1 00000005`).

- *Stage.* The old Bank is loaded as its release loads it and must be at rest: a save in progress is refused, and so is a Bank without a Pokédex or a transport box for its current save, which that release fills from the running Bank and writes at its next Save and Quit (v0.2.1 as v0.4.0). A delivery that waits is taken into the transport box, as a load takes it. The record goes into the body as above. That body is written as a new Bank under temporary names (`/m0.tmp` to `/m7.tmp`) through `BankFiles::initialize`, loaded back, and must be the same body; only then the marker `/migrate.ok` is created. It holds the way's name ("v0.2.1", "v0.4.0"), which is read only for the label.
- *Finish.* With the marker the temporary files are the Bank, whatever they were made from, and at every start that goes on here they must first load as one; if they do not, nothing is removed. Then the files of both earlier ways are removed (what is not there is not), the final files are written from the temporary ones (journal records last) and compared, and they must load as the same Bank; only then the marker is removed, then the temporary files.

Without the marker a start begins again from the untouched old files; with it, from the temporary ones. Without either, temporary files that a run cut at its end left are removed only once the current files are checked; a start that ends in an error leaves them. Because the new Bank is written through `BankFiles`, the migration follows the current files by itself. A cut run of the migration v0.5.0 shipped (the same temporary files, an empty marker) is finished the same way.

**A save in progress** of an earlier way is never settled by the migration; the last release of the way settles it (`0BAD 7`). Within each way that release reads every form in which the releases of the way bound a save in progress to its game, but one:

| Releases | Binding of a save in progress | Settled by |
| --- | --- | --- |
| v0.1.0 – v0.2.1 | v1: SHA-256 over the title and both fingerprints | v0.2.1 |
| v0.3.0 | v2: SHA-256 over the title, both fingerprints and the kind of copy | v0.4.0, after the migration's rewrite |
| v0.3.1 – v0.4.0 | v3: trainer name, ID, and 4 bytes of a SHA-256 over those and the rest | v0.4.0 |

Before it answers `0BAD 7` for a Bank of v0.4.0's way, the migration looks at its journal (`v0_4_0::Way::ready_for_its_release`). A save in progress whose binding is v2 for one kind of copy (`v0_4_0::binding`, frozen from both tags) is published once more with the v3 binding for that kind and no trainer, everything else of the record unchanged, through v0.4.0's own way of publishing a record (`BankStore::rebind`: the record not in use first, then the other, each with sequence + 1). A cut leaves the record before in force until the new one is whole, and the next start writes it again. Any other binding is left as it is. This journal record is the only thing the migration ever writes into the files of an earlier way. A failed write is `0BA2`. A cut run of the one v0.4.0 shipped, from v0.2.1 to v0.3.0, used the same marker and names for files of v0.3.0's lengths: they do not load as a current Bank, and nothing is removed; that release's migration finishes it. The result is two numbers: `0000600D` with 1 (converted), 2 (already in the new files: they open as a Bank and, without a save in progress, load whole) or 0 (no Bank, also for files that never held one, where the offline patch creates one); `00000BAD` with 7 for a save in progress or 8 for a Bank its release has to save once first; `00000BA1` to `00000BA4` for a failed step (reading the old files, or the new ones when there is nothing to convert, writing the temporary ones, removing the old ones, writing the new ones) with the console's code, or 1 for files that do not compare, 2 for a missing file, 5 for files that do not load as a Bank.

### The journal

Checksums use CRC-32/ISO-HDLC: reflected polynomial `0xEDB88320`, initial state `0xFFFFFFFF`, and final inversion. [checksum.rs](../crates/offline-core/src/checksum.rs) updates one byte at a time through a 256-entry table generated at compile time. Each linked payload holds one read-only 1 KiB table, with no runtime initialization. One-shot and incremental checksums are identical to the bitwise calculation, so stored bytes and format versions are unchanged and no migration is needed. The linker rounds payload regions to 4 KiB pages; the allocation increase can exceed the table's size.

[format.rs](../crates/offline-core/src/format.rs), [store.rs](../crates/offline-core/src/store.rs). The record names the copy of each file that belongs to the current save and that copy's CRC-32, the same for a save in progress together with what identifies its game, and a delivery from Transporter that waits. A copy belongs to a save only if its bytes have the checksum the record names. Bank and Transporter read and write it with the same code. 140 bytes, little endian:

| Bytes | Field | Written by |
| --- | --- | --- |
| 0..4 | `BKJ`, version 1 | both |
| 4..8 | Sequence, from 1 | both |
| 8 | Bit 0: a save is in progress. Bit 1: a delivery waits. Bits 4..8: the game of the save in progress, 1 to 8 (X, Y, Omega Ruby, Alpha Sapphire, Sun, Moon, Ultra Sun, Ultra Moon) | Bank; Transporter sets bit 1 |
| 9 | Copies, one bit each, 0 for A: bits 0..3 the Bank file, the main file and the transport box of the current save; bits 3..6 the same for the save in progress | Bank |
| 10, 11 | Pokémon in the transport box: current save, save in progress | Bank |
| 12..24 | CRC-32 of the Bank file, the main file and the transport box: current save | Bank |
| 24..36 | The same: save in progress | Bank |
| 36..40 | CRC-32 of the delivery that waits | Transporter |
| 40..72 | Binding of the save in progress: trainer name (24), trainer ID (4), hash (4) ([An interrupted save](#an-interrupted-save)) | Bank |
| 72..104 | Fingerprint of the game's save before | Bank |
| 104..136 | Fingerprint of the game's save after | Bank |
| 136..140 | CRC-32 of bytes 0..136 | both |

No byte is unused. Without a save in progress everything that belongs to one is zero, and so is the delivery's checksum while none waits; the spare bits of bytes 8 and 9 are zero. A record that breaks this, or one of the rules below, is refused whoever wrote it (`format::validate`).

- **Two replicas.** A new record is written to the replica that was not selected, synced and read back, then to the other. Both carry the same sequence; the higher valid sequence counts, and two valid records of one sequence that differ are an error. A record that does not read or fails its checksum counts as damaged, and the other decides. A record with a valid checksum and another version is an error, never a reason to fall back.
- **A save never writes a copy in use.** The Bank file and the main file of a save in progress are the copies the current save does not name. So is its transport box, except while a delivery waits: the delivery lies in the copy that is not in use and has to outlast a save that is undone, so the new box goes over the box in use, which is empty then (`Save::next_mover`).
- **A delivery waits only beside an empty box**, in the transport box's copy that is not in use. The record that makes a save current clears it in the same write; a save that is undone keeps it.
- **New content first.** Every copy is written, synced and read back before a record names it.

### Saving and loading

[store.rs](../crates/offline-core/src/store.rs) holds the journal and the two copies of the Bank file, [pair.rs](../crates/offline-core/src/pair.rs) the two copies of the main file and of the transport box, [bank_files.rs](../crates/bank-common/src/bank_files.rs) the order.

- A save: ask whether the game's Game Card is there, before anything else; check the prepared game ([Game saves](#game-saves)); read the game once for its before-image and the image to be written, and verify the before-image against the game as it was loaded (a cartridge taken out by then ends the save with nothing written, [When a job cannot finish](#when-a-job-cannot-finish)); write the main file and the transport box into the copies the record will name; `prepare_transfer`, which writes the Bank file's spare copy and then the record with the save in progress and the checksums of all three; write the game; read the game back; `reconcile`; read the Bank, which must be the body the save staged, by its checksum. A before-image keeps the save before, an after-image makes the new one current. After its own write (`Job::Finalize`) the worker commits only once the whole game is the after-image, with the 16-byte secure pair of the image it prepared, which is new with every prepared image; anything else is settled at once from what the game holds ([When a job cannot finish](#when-a-job-cannot-finish)). The store blocks on anything else; the worker then chooses the save itself ([below](#an-interrupted-save)).
- A load reads the journal, then each file once into its place in the body, and checks its CRC on that pass. The files hold no marker of their own. The format is in the body's header, which the main file holds; a header that is not format 2 with 100 boxes is an error (`7A000104`).
- The Bank is read once per session, by its opening (`Job::Open`, or `Job::Recover` for a save in progress). Loading the chosen game (`Job::LoadGame`) checks the game and its secure value and keeps the body the opening restored: nothing between the two writes it. Game selection, the scene set-up (`002af12c`) and the load's set-up (`002afe38`) build screens, read the found games and their secure values, and choose the game (`00229df0` sets the save manager's `+0xc8`); the trainer's reader `0026de9c` only reloads the Pokédex views from the body.
- **The main file is needed.** If its copy for the current save is missing or does not have the record's checksum, the load is an error (`7A000101`).
- **The transport box is needed while it holds Pokémon** (`7A000201`). A box that the record says is empty and that cannot be read is shown empty, and so are missing transport files, which the next save creates. A delivery that waits and cannot be read is not shown and not saved over: Save and Quit is then refused (`7A000203`), because the record of that save would say that nothing waits any more.
- With two copies a file in use is never the one being written, so none of these errors can come from a power cut.
- A new Bank writes the first copy of the main file and of the transport box, then creates the four files of the Bank container zero-filled, writes the first copy of the Bank file, and publishes the first journal record last. A start that finds no valid journal record, with at least one record still empty (zero or absent) and nothing in the second copy of the Bank file, which only a save writes, treats it as "no Bank yet" and finishes the creation in place (`BankStore::reinitialize`, which discards the four units and begins again). No Bank that was ever current can be in that state: it has a journal record, and after its first save a second copy. Two unreadable records are never taken for it; that is fault `5`. Beside a Bank that exists or cannot be read, a creation writes nothing. Until the first record exists Transporter finds no Bank and delivers nothing.

### The Miles state in the body

Everything about Miles is stored with the Bank body, in the main file ([rewards.rs](../crates/offline-core/src/rewards.rs), [native_blob.rs](../crates/offline-core/src/native_blob.rs)):

| Body offset | Size | In the original | In the patch |
| --- | --- | --- | --- |
| `160` | 6 | Date and time up to which Miles were counted | Date and time of the last Save and Quit, from where hours are counted |
| `170` | 4 | Miles balance | The same |
| `174` | 4 | The server's pass count, last seen | Day of the last redemption: u16 year, month, day. Anything that is not a date is "never redeemed" |
| `166` | 2 | Nothing: the two bytes after the reward date | Remainder in Pokémon-hours. A save writes 0..719; a larger number is paid out at the next load like any other |

The original has one reader and one writer of `174`, the accessors `002ba524` and `002ba53c`, both called from claim state `0x1B` only (`002aac1c`, `002aac3c`): it stores the session's count there when that has grown, and then sets the flag at `179`. Both calls lie behind `cmn r0, #1; beq 002aac54` at `002aac04`, which skips them while the session reports no count. The reward hook presents the count as -1 for every call of the claim task ([Rewards](#rewards)), so the original never reaches the field. The builder and the verifier check those two words. Nothing in the original addresses the two bytes at `166`: every user of the date (`001d5880`, called from `002aa7e8`, `002aacfc`, `002ad42c` and `002aea04`) reads and writes its six bytes, and the initializer does not write them.

**Starting values.** Every way a Bank comes into being sets both fields explicitly:

| A Bank that is | `174` | `166` |
| --- | --- | --- |
| created by the offline patch (`Runtime::introduce`, after the original's defaults) | zero: never redeemed | zero |
| downloaded from the server (`download::write`) | zero, not the server's count | zero |
| converted from v0.4.0's files | zero: the day of a redemption is not kept | the remainder from its rewards record |
| converted from v0.2.1's files | zero | the record's thirtieths × 24; `160` is the day the record is accounted through, 00:00 |

A value at `174` that is not a calendar day reads as "never redeemed", so no content of the field can stop Bank.

### An interrupted save

A save in progress (`Phase::Prepared`) is settled by the next start, in `Job::Recover` (`settle` with `Rule::Start`, [storage_worker.rs](../patches/bank/src/storage_worker.rs)). The journal holds the fingerprint of the game's complete save before and after, and a 32-byte binding ([transaction.rs](../patches/bank/src/transaction.rs)): the trainer's name (12 UTF-16 units, 24 bytes), the trainer ID as the original shows it (4 bytes), and the first 4 bytes of a SHA-256 over the title, both fingerprints, the kind of copy the save was made with (cartridge or installed), the name and the ID. Name and ID are read when the game is loaded, with its fingerprint (`dex::trainer`, through the original's `0026de9c`), and written with the fingerprints in the one record, so a save in progress always has them. Nothing is matched by them; they are for the message of the last row. To the storage code the binding is 32 opaque bytes. The worker compares the game's file with the two images:

| The game of the journal's title | Decision | Code |
| --- | --- | --- |
| Its file is the before-image | Keep the save before | `reconcile`; the platform secure value must be the file's (`require_secure`) |
| Its file is the after-image | Make the new save current | `reconcile`; the platform secure value is advanced if the cut came before that (`finish_secure`) |
| Its file is neither, on the kind of copy the save was made with (`Found::SameKind`) | By what the save moved | `by_moves(.., true)`, `moved::choose` |
| Its file is neither, on the other kind of copy (`Found::StandIn`) | As for a game that is not there, next row | `by_moves(.., false)`, `moved::choose_unseen` |
| Not among the games the scan loaded (`NativeGameError::NotLoaded`, `Job::Recover { game: None }`) | By what the save moved if that was one way; otherwise the save waits: nothing is written and the reply is `Reply::Waiting` with the title and the trainer | `by_moves(.., false)`, `moved::choose_unseen` |

**A save that waits** is not an error. The hook shows the original's message `0xA` with the trainer's name and ID ([Tasks and routing](#tasks-and-routing)) and ends task 9 through cleanup, where the files are closed, then the start screen. The worker keeps no failed state for it, so the next START opens the files again and settles the save if its game is there. Three related checks have numbers of their own: a record whose title is none of the eight games is fault `5`; a game object of that title that is not what the patch expects is fault `A`, as when a game is loaded; a game loaded while a save is still in progress is fault `10`. An opening settles a save in progress or ends there, so the last cannot be reached.

A file that is neither image, on the same kind of copy, was written since the cut: by the game played on, by a new game started on it, or it is another cartridge. Nothing in it tells for certain which image it was made from, and the three are not told apart.

**The kind of copy.** The original holds one copy per title: its mount (`00163F24`) opens archive `567890B4` for the title on medium 2, the game card, and only if that fails on medium 1, the SD card. When the copy of a save in progress is gone, the other kind stands in under the same title with an unrelated save, and the game must count as absent. The console says which kind a loaded copy is: the reply to the secure-value query (`0876`) carries a flag for a title on a game card, the one the original's check at `0016443C` uses to accept any value for cartridges (`PlatformSecureValue::gamecard`). At recovery the binding is computed for both kinds from the record's own name and ID (`transaction::bound`); the one that fits tells which kind the save was made with. An exact image is accepted from either kind. A binding that fits neither is fault `B`, also when no game is there to look at: that is a damaged record, or a save in progress begun by a build with another form of binding, which only that build finishes. A record holding anything else there, such as a whole SHA-256, does not come out of its own first 28 bytes again; no other form is read.

**What a save moved** (`BankFiles::pending_moves`). The copies of both saves are still on the card, and the record names them. The Bank file of each is read into the staging buffer in turn, and the identity of every occupied record is collected (`sections::stored_identity`: encryption constant, personality value, trainer ID and secret ID, all in the record's first block):

| | Save before | Save after |
| --- | --- | --- |
| The 100 boxes | Every occupied record | Every occupied record |
| The transport box | What a load showed: its own box, or the delivery it took (`transport::on_load`) | The copy the save wrote |

The two lists are compared as multisets ([moved.rs](../crates/offline-core/src/moved.rs)). What only the save after holds was deposited; what only the one before holds was withdrawn or released; a Pokémon moved inside the Bank is in both.

| Deposited | Withdrawn | `choose` (a game is there) | `choose_unseen` (none is) |
| --- | --- | --- | --- |
| some | none | Commit | Commit |
| none | some | Keep | Keep |
| none | none | Keep | Keep |
| some | some | Commit | Wait |

The first two rows cannot lose a Pokémon whichever way the game's save went, and the third cannot lose the Miles of a claim. The last row has no such answer: after a commit, if the game's save had not been written, the withdrawn Pokémon are in neither place.

- The chosen save is made current through `reconcile` with that image's fingerprint (`BankFiles::reconcile_as`): the journal makes a save current only with one of its two images, and refuses any other fingerprint.
- No secure value is checked or changed in the last three rows of the first table. If a game that was not there holds the after-image and the cut came before the original writer advanced the platform value, that value is one step behind; the next load of that game advances it (`finish_secure` in `Job::LoadGame`).
- After Bank's own write (`Job::Finalize`) the same code settles it at once (`settle` with `Rule::AfterWrite`): a game that is neither image is settled by the moves only if they went one way or none, and a game that cannot be read leaves it to the next start ([When a job cannot finish](#when-a-job-cannot-finish)).

### Hand-over from Transporter

[transport.rs](../crates/offline-core/src/transport.rs) holds these rules as tested functions. The Transporter patch runs `transport::check` and `transport::deliver` from that file; Bank's tests deliver with the same functions.

- The transport box file is the native transport box: 30 records of `E8` bytes, then 30 format-tag bytes. The journal says which of its two copies is Bank's box and how many Pokémon it holds.
- **Transporter may deliver** (`check`) while the journal has no save in progress, the box in use holds no Pokémon and no delivery waits, and while both journal records and the copy it would write can be read. It asks before a session begins and shows the original's message for the reason (`ui::refusal_message`); `deliver` asks again before it writes.
- **Transporter delivers** by writing the complete box the original Transporter built into the copy that is not in use, syncing it and reading it back, and only then publishing a journal record that says a delivery waits, with the box's CRC-32. Until the first replica of that record is durable there is no delivery; a cut before it leaves a copy that no record names. From then on there is one, and that is what the delivery answers: if the second replica cannot be written the answer is still "done", the journal is as after a cut between the two, and Bank's next save writes that replica. If the first one fails, the journal is read again (`Journal::announced`): it may be durable all the same, with only its read-back failed. Both records read and the new one is in force: "done". Both read and the one before is still in force: nothing was delivered. Anything else, a record that does not read or another record: `DeliverError::Unconfirmed`, Bank may hold the delivery.
- **Bank loads** the copy the record names. If a delivery waits, the box in use is empty, and the delivery becomes the box, unchanged (`on_load`). A load never writes.
- **Bank saves** the box into the copy that is not in use, or, while a delivery waits there, over the empty box in use. The record that makes the save current says that nothing waits any more: a delivery is taken exactly once, and no step follows the save. A save that is undone leaves the delivery waiting, whole. Once a saved box is empty Transporter may deliver again.

Occupied slots are counted by decrypting each record's species word with the standard stored layout.

### Edits to the original

57 regions (56 words and the start-up hook) and thirty-two entry functions. The builder checks every original word before patching. A site that goes to the patch branches to an entry function by its name, as in the Bank patch: the builder's profile ([transporter15/offline.rs](../crates/patch-builder/src/transporter15/offline.rs), `EDITS`) names them, Rust functions and assembly stubs, and takes their addresses from the linked ELF, which must define each as a global ARM function. Where a site leaves the original's flow for good, it is one branch to a stub in the payload, and the stub goes on inside the original itself; the original holds no decision logic of the patch. One entry, the layout check for `0013AEE4`, lies beside the start-up hook (see [Placement](#placement-1)).

### Placement

Same method as the [Bank patch](#placement). Transporter's main function is the same engine code as Bank's: `00103D9C` is its one `BL` to application init. The start-up hook, the same code as Bank's (`patch-common`), sits at `0028D1AC`, in the zero bytes after the original text. The layout check for `0013AEE4` lies there too, after the hook (section `.patch.bootstrap.check`): that site is on the way of every layout, and the first layouts are built during start-up, before the payload is executable (a branch into the payload from there was a prefetch abort at its entry word). The check hands only a layout binary of the language screen's size to the payload, and that layout is built when the screen is opened. No site that only the language screen runs can stand in for this one: its constructor (`0022BD28`) reaches `Layout::Build` through `001A1964` and the set-up function `0022C438`, which eight screens share (vtable slot `+0x2C`). That function sets up the screen's resources (`0022ECC8`, called with the screen's archive table; taken to be the archive load, not traced) and builds the layouts (`0022E8AC`, then `001DD234`, `0012ECC8` and `0013AE2C`) in one go, and the one call it makes back into the screen (vtable slot `+0x28`) comes before both. The layout binary is first looked up inside `0013AE2C` itself, at `0013AEE0`. The hook flushes the caches whole (Luma SVC `92`/`94`): the payload's code range is small, and a range flush of a small range is carried out by virtual address on every core, which faulted in the kernel on core 1 under another process's address space. The payload links at `00364000`, the first page after the original zero-initialised data, which follows the data section directly (`003293FC..003638A4`) and is not page aligned. The paired exheader enlarges the data segment and sets BSS to zero (fields `0x34`, `0x38`, `0x3c` only); the IPS writes the former BSS as zero, then the payload. `code.ips` and `exheader.bin` only work together.

### Tasks and routing

The original's tasks are called steps here, after its router `get_next_state`.

The factory `0019CEE4` makes steps `0..0x12` (`cmp r1, #0x13` at `0019CEE8`) and installs each task's vtable; a task's update is its vtable's `+0xC`. Every hook that is given a task first checks that its vtable is that task's (`Task::from_raw`), as Bank's hooks do:

| Step | Vtable | Native update at vtable `+0xC` |
| --- | --- | --- |
| 1, language task | `002E6680` | `0024538C` |
| 6, transfer | `002E6A90` | `0024A0C4` |
| 7, game search | `002E6774` | `00246F04` |
| 8, game list | `002E6618` | `002445A4` |
| 9, reading the game | `002E66B8` | `002455D0` |
| `0xB`, Bank task | `002E6970` | `00248C68` |
| `0xC`, question | `002E67C4` | `00247304` |

The search entry takes the search, delivery the transfer, every game-list hook the list, and each update entry its own task. Given another object, a hook does not touch it again, as Bank's hooks do: the search and the update entries answer finished, delivery fails before anything is written, the entry-card hook counts the card as gone, and the other game-list hooks leave it as it is (the list-next stub without the store it replaces). Every pointer a hook reads from an object of the original is checked before it is followed (`patch_common::native::follow`): a list task whose manager is not a pointer lists no cartridge or save and counts its card as gone, and the language screen leaves out what it cannot reach (the Back button's text, the placing of the panes, the disabling of the hidden entries). The cartridge task and the language screen are not tasks of the factory and are not checked. The search, reading, the Bank task, the question and the transfer are entered as Bank's tasks are: their update slots in the vtables are edits, which name the original updates, and each entry calls the original update behind its own work. The builder and the verifier hold the factory's bound and cases, the vtables' addresses and the other update slots; the verifier also keeps the factory, each vtable's first three words and those slots unchanged.

- **Routing.** The original's router `get_next_state` (`00242BA0`) is called from one place in the manager's step function (`00242EF8`), with the finished task and its outcome byte (`task + 0x30`). The router entry calls it and changes four answers (`navigation::destination`, tested on the PC against a transcription of the router's cases in [router.rs](../patches/transporter/src/router.rs)): after the game list with a chosen game comes the reading of the game, where the original answers "connect"; after the reading comes the Bank task, whatever the outcome, where the original's server tasks came in between; where the original answers the cancel task `0xF`, the disconnect task follows ([below](#tasks-and-routing-1)); and so it does where the original answers the failure task `0x12` (`002444BC`), which shows message `0x0B` after the Bank task or the transfer ended with outcome `0xF`: offline each of them has shown its own message by then. A cancelled task (the manager's flag `+0x1A`) gets the disconnect task, the original's own answer, as Bank's cancelled task gets cleanup. A manager or finished task that is not a pointer, or a task number the factory does not make, gets the disconnect task without the original being asked, as Bank's router hook answers cleanup; both read the ended task and ask their router through the same code (`patch-common`'s `native::Ended`). An answer of the original the offline flow does not take (`navigation::TAKEN`: the language screen, the start screen, the search, the list, the question, the transfer, disconnect, reload and exit) gets the disconnect task too, as Bank's router hook sends every answer it does not take to cleanup; the tests show that this changes nothing from a task the offline flow enters. Nothing inside the router is edited.
- **Check at START** (game search, `00246F04`, the task after the start screen). Its states: 0 start the cartridge scan, 1 wait for it, 2 look for Virtual Console titles, 3 end with "found", 4 show message 0 ("Could not find a game…") through `0019B50C(ui, 0, 1)` with the ui at `task + 0x34`, 5 wait for the acknowledgement and end with "none", which the router answers with the disconnect task and then the start screen. The search entry replaces the update in its vtable, as Bank's scan entry does. In state 0 it asks `transport::check` on the worker thread, which reads Bank's journal, and then: runs the original update, which goes on with state 0; returns 0 to come back next frame; with a message on screen selects state 5, as the original does after its own message (`00247000`); or, for a task with no dialog owner, ends with "none" as state 5 does (`0024702C`). Every other state is the original update's. An unexpected task ends at once, with nothing read or written, as Bank's task hooks answer one. The message is the original's 5 when Pokémon are in the way, in Bank's transport box or in a delivery that waits, and its 3 when there is no Bank, a Bank save is not finished, or a file does not read (`ui::refusal_message`); the entry shows it with the call state 4 makes. Those are what Bank resolves: its start creates a Bank and settles a save, its next Save and Quit replaces a file a power cut left unreadable, and it names a Bank of an earlier release (files of another size), as it does an archive not there yet, which its start creates. What Bank cannot resolve is the error screen with Bank's own numbers (`storage_worker::check_reply`): an archive or file that does not open for any other reason (`bank_common::fs::Visit::unreachable`, `fs::Error::bank_resolves`), fault `3` with the console's result, and both journal records damaged (`Refusal::Damaged`), fault `5`, as Bank stops on them. A worker that cannot be used is the error screen too ([Worker thread](#worker-thread-1)). The original shows message 3 from a reply listener of its sign-in (`0025C964`) when the server asks for a cleanup. The check runs at every START, so a second transfer in one run meets it again.
- **Loading panel after START.** The original's search shows none. The game list's own indicator ("Die Spielesoftware wird überprüft…") belongs to the list's screen: the list's set-up builds that screen in its state 0 (`0024264C`, which loads its archives 52, 45 and 43 and their layouts) and only then starts the indicator on it (`002450F4`). The patch reads Bank's files and looks for saves on the SD card in the search, so the search entry starts, on its first frame, which does nothing else, the general loading panel of the shared UI (`task + 0x34`), which needs nothing loaded: `0019B340(ui)`, as the reader's set-up starts it (loop sound `0x50011`, pane `0x1D`, its spinner animation 0). Its text is the list's: message `0x20` of text file 39, which the panel's own file 23 has not; the entry shows the text frame as `0019C700` does (pane `0x1E` shown, `0x25` hidden) and copies the message into pane `0x23` with `0019F7B0`, from the file opened as the language screen's Back text is ([Language screen](#language-screen)), on the UI's heap (`[[ui + 0x78] + 4]`). That one panel stays until the game list is on screen ([panel.rs](../patches/transporter/src/panel.rs)). The list's call of `002450F4` (`00244EAC`) goes to a stub: while the panel is up it enters `002450F4` at `00245180`, with that function's own prologue, which only notes the list's start time at `task + 0x70` for its minimum time, so the list starts no indicator, sound or text of its own; the list-started entry then moves that time back by as long as the panel has been up, measured as `0019B758` measures (`00233854` notes the original's clock when the panel goes up and now, `0025A77C` gives each in ms), so the list's 3 s count from START and it appears as soon as it is built; otherwise it makes the call. The list's set-up checks every frame whether its indicator's animation `0x4F` stands idle at frame 0 and then plays `0x50011` again (`00244D40`..`00244D88`); an animation that was never bound reads so, and `001A220C` would start the loop on another of its 11 players each frame, so while the panel is up the stub at `00244D40` goes on behind the check (`00244D8C`). Once 3 s have passed since the start time, the list's end of loading (`00244B24`) stops `0x50011`, which is the panel's sound, hides its panes `0xB7` and `0x4D`, which were never shown, and unbinds `0x4F`, which `0019B604` skips when it is not bound. The panel ends as the question task ends it when no message follows (`00247394`..`002473D8`: stop `0x50011`, hide `0x1D`, unbind animation 0, then `0019C814(ui)`, which hides the panel, its text frame and the dialog frame, the state the shared UI's constructor leaves it in, `0024B778`): when the list is on screen, through the list-ready entry; before a message that waits, through the message entry (a refusal, "Could not find a game…"), after which `0019B50C` shows its own dialog frame; and when the search ends in any task but the list, through the router entry. It is started once per search and ended once. Without what the panel and its text need (the UI's context, its work strings and layout, its heap, text file 39), nothing of it stays and the search stops on the error screen with fault `2`, as Bank's hooks do for an object they do not expect: no file work without its panel. The entry answers "come back next frame" on the panel's frame and until the panel has stood for 0.5 s ([Loading screens](#loading-screens-1)); then the worker is started, on the first START of a run, and the check handed over.
- **Bank task** (`00248C68`, after the game is read). The original asked the server here whether Bank can take the Pokémon. Its other messages are `0x23` ("the server has been locked") and `0x22` (no Game Card). After a "yes" it continues at `00248E44`: unless the Game Card was removed (message `0x22`), it writes its note into the chosen game ([below](#the-originals-note-in-the-game)), starts saving that game (`0024B92C`, mode 2) and waits for the save (`0024B868`) before it ends with "allowed". The patch branches from the task's first instruction (`00248CDC`) to `00248E44`, so the request and its reply are never entered and the note and the save happen as before. Nothing has been written to Bank in this task: a Game Card that is gone before the note save (`00248E68`, a card entry) shows the failure message (`00248EBC`) instead of `0x22`, from its second page, and a note save that fails takes the same path (`00248F88`), where the original ended without a message. Either ends with outcome `0xF`, then disconnect. The task learns of a failed note save from its own poll (`[vtable + 0x1C]`, `0024B868`: 1 saved, 2 failed, `00248F68`..`00248F88`) in the frame the save ends, and shows the message in that same call. For a note save the error screen stands for (the next table), the message-text entry notes its numbers while the Bank task's update entry (`transporter_bank`) runs the original update, and the entry puts the error screen in its place on the task's shared UI (`task + 0x38`) before the frame is drawn, holding the failure as the search and the transfer hold theirs.
- **Question task** (`00247304`). Counts the transport box (`0024D624`) and at zero shows its own message and ends the session.
- **A session without a transfer** (the Bank task or the question ends with outcome `0x10`: nothing to move, or "No"). The original router answers the cancel task `0xF` (`00248360`), which asks the server to drop the transfer that was begun and keeps the general panel with "Datenübertragung über den Server…" up for at least 1.5 s (`002484E4`, `00248470`); it saves nothing. Offline nothing was begun, so the router entry answers the disconnect task instead (`navigation::CANCEL`), and "Software wird beendet…" follows the question's message directly.
- **Transfer** (`0024A0C4`). Original sub-states: 0 create request, 1 serialize the data object and upload it, 3 save the source game without the Pokémon, `0xA` commit request, `0xE` final save, `0x10` success message, `0x11` failure message. Sub-state `0xA` is never selected: its one setter (`0024A3C0`) selects `0xE`.
  - **What the delivery answers** (`storage_worker::delivered`): Bank holds it (`Delivered::Done`), and the original goes on to remove the Pokémon; Bank holds none for certain (`Delivered::Undelivered`), because its files refused it on the check before the write, as they would at START, or the SD card had no room for its write (`patch_common::fs_result::lack_of_space`), and the entry answers "failed", sub-state `0x11`, whose failure message gives way to the refusal START shows for it (`ui::refusal_message`), or to "The SD card is full."; another write the SD card refused, or a file Bank cannot resolve, is the error screen; whether Bank holds it cannot be told (`DeliverError::Unconfirmed`), and the stub goes on at `0024A2A8`, the original's message `0x22`, sub-state 4, outcome `0xF`, as for a game that cannot be saved after the delivery, in whose place message 3 comes, to open Bank; the worker cannot be used, or the box is no box, and the transfer stays in sub-state 0 on the error screen ([Worker thread](#worker-thread-1)). The entry notes its answer for the message that follows (`ui::Delivery`, one word that the message-text entry takes).
  - **Before the delivery** the entry asks, once the transfer's panel has stood for 0.5 s and as the original asks before each save of a DS game, whether the chosen cartridge's card is gone (`cart::chosen_card_missing`: the original's skip of Virtual Console titles, then `Saves::card_missing`). If so it answers "failed" and writes nothing: sub-state `0x11` ends the loading panel and shows the failure message, outcome 2, then disconnect. So the Pokémon never reach Bank while the game they leave cannot be saved.
  - **The failure message** `0x0B` is "The server did not receive the data." and, on its second page, "Please confirm that your Game Card is properly inserted, and then try again." There is no server, so it is shown from its second page wherever it comes (`ui::shown`): the message-text entry stands in for the load of the message in "show a message" (`0019B578`, `001DBEB8(messages, message, string)`) and keeps what follows the first page in the string before the dialog gets it (`patch_common::ui::keep_rest`), or behind the first line in Simplified Chinese, which has one page. Message `0x0B` is shown by sub-state `0x11` (`0024A5AC`), the Bank task (`00248EC0`) and the failure task (`00244528`), which is never reached. ### Screens

Texts are in the GARC `a/0/0/6` of the RomFS, file 23 for English (Game Freak text format). Used here: `0x03` the last session did not complete, open Pokémon Bank; `0x05` transport box not empty; `0x08` no Pokémon to move, `0x0A` moved, `0x0B` failure, from its second page but on the error screen, `0x10` nickname notice, `0x11`..`0x15` and `0x41` Pokémon that cannot be sent, `0x16` held items returned, `0x22` no compatible Game Card detected, `0x27` "Press HOME to return to the HOME Menu"; and message 0 of file 26, "The SD card is full.", its first line.

**The error screen** is Bank's ([The screen that stays](#screens)), from Transporter's own file: `0x0B` up to the end of its first part, and after A `0x27` with the version on its second line and the two numbers on its third (`ui::stop`; `0x27` is one line in all ten languages), made by the same functions as Bank's, and the line alone where it does not all fit. Both are loaded by "show a message" without a wait (`0019B50C(ui, message, 0)`, whose flag goes to `00233FA8`, the same code as Bank's `0029749C`), so the dialog does not end; the text is cut and joined in the shared UI's string object (`ui + 0x8C`) and handed to the dialog again (`0019C7D4`), and every later frame only calls the dialog's poll `0019B4BC`. The numbers are Bank's (`bank_common::fault`): `2` for a worker that cannot be used, with its own second number, and for an object of the original the search or the delivery cannot reach (the shared UI's parts for the panel, the transfer's manager), second number 0, `3` and `5` where Bank's files cannot be reached or the journal is damaged ([Tasks and routing](#tasks-and-routing-1)), `D` for a note save of a save on the SD card the card refused or may have left half-written, or of a Virtual Console title, with the console's result ([Tasks and routing](#tasks-and-routing-1)), and `14` for a delivery that did not happen and that Bank holds nothing of: its write the SD card refused for another reason than lack of space (the console's result), its journal or transport file did not take it (3), or it was handed no whole box with Pokémon (1, or 2 without Pokémon), which the question task makes impossible (`storage_worker::delivery_reply`). A hook given an object that is not its task has no screen to show it on and answers as before (finished, or a delivery that failed), as Bank's hooks answer one. A failure is held in the task where it came (`Runtime::report_failure`; a screen that cannot be shown ends the task as it would end without one): the search stays in its first state, the Bank task in the state after its failure message and the transfer in sub-state 0, and their entries keep the screen; a job still out is waited for first, then the loading panel ends and HOME and sleep are let through.

The question task shows one fixed sequence when the reader flagged anything (`002474E8`..`00247648`): message `0x11` (there is a Pokémon that cannot be sent) if `info + 0x1C0` is set; then one message per reason flag, `0x12` for an Egg (`+0x1C1`), `0x13` for a fused Kyurem (`+0x1C2`), `0x14` for a problem with a Pokémon (`+0x1C4`), `0x41` for too many held items (`+0x1C6`); then always `0x15` (the Pokémon were removed from the Transport Box). A Pokémon refused by the local checks therefore produces three dialogs, as it did with the server. The patch does not touch this sequence.

### Bank data object

Transporter contains Bank's data object (constructor `0010D8EC`, initialiser `00115410`, body `BB518` bytes). Startup allocates `BB530` bytes (`00106234`..`0010623C`), calls the constructor at `00106248`, and stores its result at `manager + CC` (`0010624C`). The constructor loads vtable `002E6DD0` from `0010DA38` and installs it at `0010D8FC`, before calling the initialiser at `0010DA2C`.

- **Reaching it from a task:** `[task + 8]` manager, `[manager + CC]` data object, `[object + BB524]` transport accessor, `[accessor + 4]` body pointer.
- **Transport box:** record `i` at body pointer `+ AAF1C + i * E8`, tag `i` at `+ AD604 + i` (the body offsets under [Native body](#native-body) plus 8).
- Reading a game (`00245460` for Gen 5, `002463D8` for Gen 1/2) clears the 30 slots and stores each converted Pokémon at its source position through `0019A6F4`, which also writes the tag from the Pokémon object's `+0x10`.

The patch checks the object's vtable before it follows the transport accessor (another fails the delivery before any file work), then copies the 30 records and 30 tags as they are. The builder and the verifier hold the constructor's vtable literal and its store, the allocation size and the store at `manager + CC`; the verifier also keeps the constructor and the vtable unchanged.

### File access

Transporter's SDK has the same file calls as Bank's ([File access](#file-access)): OpenArchive `001DB7DC`, CloseArchive `001DB7AC`, OpenFile `00159230`, Read `0015930C`, Write `00159390`, GetSize `001593F0`, CloseFile `00159364`, each with the same instructions and command words as Bank's; it has no CreateFile. Its `fs:USER` session is at `00311F80`. [program.rs](../patches/transporter/src/program.rs) names them (`Transporter15`, with `FS_SESSION`), without CreateFile and DeleteFile.

- Bank's extdata: through `bank-common`, as every patch of Bank reaches it ([fs.rs](../crates/bank-common/src/fs.rs), `fs::Visit` with Transporter's calls): the Bank container for its two journal records, and the transport box, one at a time, each with one archive handle and one open file ([Files](#files)). Transporter visits them (`Split::visit`): it reads and writes the files that are there, and creates, deletes or replaces none. A file that is not there or does not open makes every read of it fail, unlike for Bank, which reads a missing one as zeros; the check then refuses at START, and Bank's next Save and Quit makes the file whole. The host tests run the delivery rules on a simulated card that does the same (`testing::Visit`). Transporter's exheader grants neither archive: its storage info lists only its own extdata id (`C9C`), and its filesystem access mask (`0x10`) has no SD card bit. Both work because Luma3DS's own process manager registers every process with a filesystem access mask of all bits (`sysmodules/pm/source/launch.c`, `loadWithoutDependencies`: "Not in official PM: patch local caps to give access to everything"), whatever the exheader says and for every title. Luma3DS has had its own process manager since v10.0. The paired `exheader.bin` therefore leaves the access fields as they are.
- SD card ([sdcard.rs](../patches/transporter/src/sdcard.rs)): the identity read of the scan, the read and the write of a save and its backup are plain code over a file of the card, tested on a simulated one (short reads and writes, a backup that does not close), as Bank's file layer is. On the console the card is archive 9 with an empty path, each file opened with its archive in one call (open-directly `001DF448`); the calls on the open file are `patch-common`'s `file`, as for Bank's files.

### HOME button and sleep

Same mechanism as [Bank](#home-button-and-sleep), in the same engine code: mask at `002F49E8 + 2`, set `0022AEEC`, clear `0011A5FC`. A HOME press is accepted only while the mask is zero (`0010AD78` then sets the flag at `+1`), and the main loop carries an accepted press out some frames later without looking at the mask again (`001044D0`). The original sets bit 1 in the connect task (`00248B58`) and clears it in the disconnect task (`002470F4`).

The original set bit 1 once for its whole online session. The patch follows the rule of the Bank patch instead: refused while files are read or written, let through on every screen that waits for the user.

- **By the kind of the next task.** The router entry (`hooks::transporter_next`) replaces the manager's call of the router. After the original has answered, `navigation::destination` gives the next task and `navigation::loads` says whether it reads or writes: the game search (with the Bank check in front and the cartridge scan), the game list, reading the chosen game, the Bank task (its record save), and the transfer; and the question, whose first state takes down the panel of the reading. For these the entry sets bit 1; for every other next task it clears it, unless a job is still out, as in Bank. The question shows itself through `00199F38`, not through "show a message", so the question's update entry clears the bit, unless a job is out, in the frame its first state runs, which is the frame its panel goes down. Which tasks start a read or a save was read from their code: the search calls the scan (`00153E3C`), the list's set-up and the reader call the cartridge read (`0019ADEC`) and the list's set-up also starts the Virtual Console scan, the Bank task and the transfer store the record and begin a save; the list's update, the question task and the disconnect task call none of these.
- **The game list** both reads and waits. Its set-up (`00244D2C`, called until it reports "done") reads every listed save; its update then runs the list. The first instruction of the update's first state (`002445EC`) runs once, after the set-up and before any input, and the list-ready entry clears bit 1 there, unless a job is out.
- **A message that waits** ends the refusal. A task that reads or writes shows one where it has nothing left to do but end: "Could not find a game…" in the search (`00246FFC`), the three about the chosen game's save or card in the reader (`00246260`, `002462D0`, `00246340`), the failure message before the note is saved (`00248EC0`), and in the transfer "no Game Card" (`0024A2F0`), the closing message (`0024A54C`) and the failure (`0024A5AC`). Each sets a state that only waits for the acknowledgement and ends the task. No code of the patch ran there, so the original's "show a message" function `0019B50C(ui, message, wait)` itself is the place: its first instruction, `push {r4-r8, lr}`, is a branch to the message entry's stub (`patch-common`'s `message_stub!`, as in Bank), which runs it, calls the entry if `wait` is not 0, and goes on at `0019B510` with every register as it came. The entry clears bit 1 unless a job is out. A hook that holds the patch's state lets go of it before it calls the original, so an entry that finds the state taken runs inside a hook with no job out and clears the bit; Bank's entry does the same, as its hooks show messages and call the original's welcome and reward updates only while no job is out. The messages of the Bank check go the same way.
- **Accepted presses.** As in Bank, setting the bit also clears the flag at `+1` (`task::refuse_home`, through `patch-common`'s `home::refuse`), at every beginning of a refused task, so a press accepted in the frame before is not carried out while files are read or written.
- The original disconnect task still clears bit 1 as well. The original's own bit for a running Virtual Console save (value 4, `00251490` and `001DFAF8`) is not touched.

### Worker thread

The check and the delivery run on the same worker as Bank's patches ([Worker thread](#worker-thread) of Bank): `patch-common`'s thread and mailbox, with Transporter's SDK from [program.rs](../patches/transporter/src/program.rs) (`Transporter15`). Its SDK is the same code as Bank's: thread creation `001E3F58`, whose trampoline `0011F100` initializes native TLS and ends the thread through `svcExitThread` (`0011F140`), the delegate `0011F098`/`0011F0B4`/`0011F0A8`, and the event `001E6404`/`001E5220`/`001E3CF4`; the builder and the verifier check its priority conversion (`001E3FC8`..`001E4040`), which turns the SDK argument `0x11` into kernel priority `0x31`. The first START starts the thread; it waits for jobs until Transporter is closed, and no job ends it. The main thread owns every object of the original: the delivery entry copies the transport box into the worker's staging buffer (6,990 bytes) before it hands over the job, and the check needs nothing. The entries answer "pending" until the reply is collected; a job is kept with its kind (`Pending`, as Bank's with its task), so a job of the other kind that is still out is waited for and its reply dropped, and only then is the entry answered as failed; the main thread never runs a job and never waits for the worker.

Behind its loading screens the patch's own work on the main thread takes one step per frame, as Bank's does: the panel and its text (which opens text file 39) on the search's first frame; the worker started and the check handed over once the panel has stood for 0.5 s; later the delivery handed over with the transport box (6,990 bytes) copied into staging. ### The original's note in the game

The original keeps 32 bytes in the chosen game that are its half of a transaction with the server. `0019BA68(manager, out)` reads them and `0019A13C(manager, in)` stores them: for a Gen 5 game inside the save image the cartridge task holds (`+0x1DA00` in the active copy), for a Virtual Console title through that title's save.

| Offset | Size | Content |
| --- | --- | --- |
| 0 | 8 | ID the server gave for this copy and session |
| 8 | 8 | Transfer number; zero means "nothing in progress" |
| `0x10` | 12 | Three words of the server's reply; the first is compared together with the ID |
| `0x1C` | 1 | State: 1 started, 2 sent |

| Moment in the original | Note | Server |
| --- | --- | --- |
| Bank task, after a "yes" (`00248ED0`) | ID, number, state 1; the game is saved | remembers an open transfer |
| Transfer, after the upload (`0024A300`) | state 2; saved with the box without the Pokémon | holds the Pokémon, not yet in the transport box |
| Transfer, after the commit request (`0024A484`) | number cleared; saved | puts them into the transport box |

At the next session three server tasks used the note. Step `0xA` (`00248814`) asked the server whether a transfer was open. Task `0xD` (`00246B68`) read the note: with a number and state 1 it had the server discard its copy, with state 2 it had the server finish, then it cleared the number and saved. Task `0xE` (`00243AF4`) first compared the note's ID with the server's; another copy of the game got message 6 ("You previously used a different copy…"), with the choice of giving up the Pokémon in transit (messages `0x1A`, `0x1B`). The result was a transfer that a power failure could neither lose nor double, sorted out with the same copy of the game.

**Offline** the note is written and never read:

- The values come from the server's reply, which never arrives. The number is taken to be zero (the reply buffer was not traced to its source), so the note reads "nothing in progress"; the state byte becomes 1 and then 2.
- The three saves still happen, because they are the original's: once after the game is read and before the question, with the box in the transfer, and at the end. Tasks `0xA`, `0xD` and `0xE` are never entered ([Tasks and routing](#tasks-and-routing-1)).
- What takes the transaction's place is the order of the two writes: the delivery is written, flushed and read back before the game is saved without the Pokémon. A power cut in between leaves the Pokémon in Bank and in the game: never lost, but possibly doubled. That is the one guarantee of the original the patch does not give, and it is a decision, not a gap.
- The order cannot be closed by the journal: the delivery and the game's save are two writes in two places, and a cut between them leaves one done whatever the order. Saving the game first would turn the duplicate into a Pokémon held only by a copy no record names, which needs a recovery that reads the source game again to tell whether its save went through, and keeps the box safe from Bank's next save until then. Whether a cut can tear a Gen 5 save is not known. The patch takes the side that cannot lose a Pokémon, the rule of Bank's own recovery for a save that moved Pokémon one way ([An interrupted save](#an-interrupted-save)).
- A refusal concerns Bank's files, and its message sends the user to Bank, which shows its own numbers; Transporter shows numbers only for a failure of the patch itself ([Screens](#screens-1)). A delivery that failed leaves the game unchanged and Bank too; its message is the refusal START shows when Bank's files refused it, "The SD card is full." when the card had no room for it, and the failure message's advice to check the card and try again when the card was gone before it. Where the record announcing the delivery may have been written and the journal, read again, cannot say (`DeliverError::Unconfirmed`), the message is the original's message 3, to open Bank, without "try again": Bank may hold the delivery while the game still holds the Pokémon, a duplicate, never a loss ([Hand-over from Transporter](#hand-over-from-transporter)). A record that reads back on the second look counts as delivered, and the Pokémon leave the game.
- A swapped Game Card is not what the note guarded against within a session. The original checks its "card removed" signal (`001DE43C`) before each of the three saves and stops with a message; the patch asks it before the delivery as well, so that nothing reaches Bank while the cartridge's card is gone ([Tasks and routing](#tasks-and-routing-1)). A save on the SD card is addressed by its file name for the whole session, whatever cartridge is inserted, and the signal is not asked for it ([Saves on the SD card](#saves-on-the-sd-card)).

### Empty Gen 5 slots

The Gen 5 reader (`002455D0`, sub-state 4) runs 14 local checks (table `002AFFE0`) and a conversion on every slot whose per-slot result code (`[info + 0x48 + 4 * slot]`) is zero. The server sent `0x14` for empty slots, which skips them. Without it, empty slots fail the checks, set the "removed" flags at `info + 0x1C0`, and raise a false dialog. The slot entry answers `0x14` for a slot that holds no species ([gen5.rs](../patches/transporter/src/gen5.rs)). The Gen 1/2 reader skips empty slots itself.

The species has to be decrypted; the stored header does not tell. A box record is 136 bytes: personality value, flags (u16 at 4), checksum (u16 at 6), then four 32-byte blocks, XORed word by word with the LCG stream seeded by the checksum and stored in the order `((personality >> 13) & 31) % 24`. The games store empty slots in two forms: a slot that was cleared has personality value 0 and checksum 0; a slot that was set up and never used has personality value 0 and checksum 4, because a blank record carries the genderless flag (byte `0x40`).

### Shiny Gen 1 Pokémon

Transporter 1.2 (January to September 2017) tested the wrong DV for a shiny Gen 1 Pokémon and kept the constructor's random gender. The patch brings back the Pokémon that only that rule made shiny ([legacy_shiny.rs](../patches/transporter/src/legacy_shiny.rs)):

| Rule | Attack | Defense | Speed | Special |
| --- | --- | --- | --- | --- |
| The original's (`0024F5B8`) | bit 1 set | 10 | 10 | 10 |
| Transporter 1.2's | 10 | bit 1 set | 10 | 10 |

The patch applies it where 1.2's rule holds and the original's does not: DV bytes `+0x1B`/`+0x1C` of the source record `A2 AA`, `A3 AA`, `A6 AA`, `A7 AA`, `AB AA`, `AE AA`, `AF AA`. All four DVs 10 (`AA AA`) is shiny by both and stays the original's. Of 65,536 combinations, 15 are shiny instead of 8; every other Pokémon converts as before.

- **Where.** The Gen 1 converter `0024F428`, which has one caller, holds the 33-byte source record in `r4` throughout. The Gen 2 converter (`0024E48C`) and Gen 5 are not touched. Both entries are pure and look only at the record, so a conversion during the game search is harmless.
- **Shiny.** At the constructor call (`0024F6B0`) the construction parameters are at `sp + 0x18`; their word at `+0x0C` is the shiny mode (1 never, 2 shiny; stored at `0024F610`). The entry sets 2; the constructor makes the shiny personality value as for any other shiny.
- **Gender.** The constructor (through `0012F8BC`) draws a gender for the species (`random(252) + 1` against the ratio code), and fixed-sex and genderless species get theirs. For the ratio codes `0x1F`, `0x3F`, `0x7F`, `0xBF` the original then replaces it with one from the Attack DV (`0024F8E0`..`0024F90C`): female up to Attack 1, 3, 7 and 11. Since every shiny of the original's rule has Attack 2 or more, no shiny of a species with code `0x1F` (one female in eight) can be female. For these Pokémon the entry continues at `0024F910`, behind that code, for all four codes, and the drawn gender stays: for code `0x1F`, female in 30 of 252 draws. Nothing else is drawn.
- **Met date.** Unchanged: the converter writes the console's date (`0024F6FC`), and the rule does not depend on it.

### Cartridge and game list

- **Cartridge task** (`00243510`; mode at `+0x30`: 2 scan before the game list, 1 read, 0 write). It runs on a thread of the original and reaches the cartridge through three functions: `0021AA0C(out)` reads the four-letter game code, `0021A7E0(9, offset, buffer, length)` reads the save, `0021AB50(9, offset, buffer, length)` writes part of it. It accepts `IR` + `A`/`B`/`D`/`E` + a language letter.
- **Game list** (`00244D2C` builds it, `002445A4` runs it). An array of kind bytes at `task + 0x3C`, count at `+0x64`, cursor at `+0x66`, heap at `+0x68`. Kinds 1..4 are Black, White, Black 2, White 2; higher kinds are the 39 Virtual Console titles (table `002C2A80`). State 1 notes the cartridge's kind and starts a read (`0019ADEC(manager, heap)`), state 2 adds its entry and goes to state 3, where the Virtual Console titles follow. Confirming an entry of kind 1..4 stores the game version in the manager; the cartridge is read again afterwards.
- **Removed card.** `001DE43C(manager)` asks whether the card was taken out: a sticky event at `[manager + 0xD8] + 0x802B0` (set up at `00106338`), set by the notification that the card is out and cleared by every scan (`00153E3C`) and every read that starts (`0019ADEC`); asking does not change it. Once the card is out it answers yes for whatever game is presented, until the next read starts. The original asks before the list reads its first item (`00244F00`, then the list-next site), when a DS entry is confirmed (the list's listener `0025C520`, at `0025C5A8`; yes leads to list state 7, message 3 of the list's file, "No compatible Pokémon game…"), and before it reads or saves a DS game. Each site first skips Virtual Console titles (manager `+0x148` and `+0x14C` both set).

### Saves on the SD card

The three cartridge calls are redirected at their call sites. `Saves` ([sdsave.rs](../patches/transporter/src/sdsave.rs)) holds what is offered and which item is presented to the cartridge code right now: the cartridge slot itself, or one save.

- **Scan.** In scan mode the cartridge-id entry calls the original first, then probes the accepted file names in the [listed language](#language-screen) (4 open attempts at most). A file is taken only if it is exactly 524,288 bytes, opens for reading and writing, and holds the game and language its name says: the language byte and the game byte at `0x1941E` in each of the two copies (the trainer block `0x19400`, where the original reads name and ID; the second copy starts at `0x24000`, or `0x26000` for Black 2 and White 2) are checked by `Save::identifies`. A copy whose game byte is none of the four (20 White, 21 Black, 22 White 2, 23 Black 2) says nothing; at least one copy has to name the game and language (1 Japanese, 2 English, 3 French, 4 Italian, 5 German, 7 Spanish, 8 Korean), and no copy may name another. The original never makes this check: its validator (`0019AA30`) checks the layout (footer size `0x23F9C` or `0x25FA4`, magic `0x31053527`, block CRCs), so it would take a Black save for White or a German save for English. The version it stores when an entry is confirmed (manager `+0x148`, from the list kind) only tells DS games from Virtual Console titles, so such a save would only be listed wrongly; the check keeps the name of a file a statement about its content, as the cartridge header is. The items are kept in the order of the original's list kinds (Black, White, Black 2, White 2). A Gen 5 cartridge in that language stands at the place of its game, and the save of that game is left out. The first item, cartridge or save, is presented in the cartridge's place. A Gen 5 cartridge in another language is no item; if no save stands in its place, the entry answers a game code of zero, which the cartridge task takes as "no Pokémon cartridge" (`00243554`).
- **Calls.** While the cartridge slot is presented, all three entries pass through to the original functions. While a save is presented, the game code comes from its file name, reads and writes go to the file, and the save is copied to `<name>.sav.bak` before the first write of a session: read whole, written whole, flushed with its last part and closed, then opened again and read back against the CRC-32 of what was read from the save (`offline_core::Crc32`), as Bank's own files are read back. Each write to the save is flushed, read back through the copy buffer and closed, and counts only if the card holds its bytes and the close reports no error. Without a backup that is complete, closed and read back as the save, the save is not written and the next write tries again. A backup the card has no room for, by the original's own test (`patch_common::fs_result::lack_of_space` on the result of the open with create, or of a write that grows the copy), is noted for the failure message the Bank task shows next, which becomes "The SD card is full.". A write that fails after a write of the session reached the save (`Saves::touch`) may leave it half-written (`sdcard::WriteFault`); that, and a backup or write the card refused for another reason, ends on the error screen with the console's result ([Tasks and routing](#tasks-and-routing-1)), and the reader finds a damaged save when it is chosen again.
- **List.** The list-next entry runs after each read for a DS entry: it notes the next item's kind and starts its read, as state 1 does for a cartridge, so the cartridge and every save get an entry. The select entry notes which entry was picked. List positions are mapped back to the cartridge or a file, so an item the original rejects does not shift the others.
- **A removed card concerns the cartridge alone.** Every site where the original asks whether the card was taken out goes to a card entry ([Cartridge and game list](#cartridge-and-game-list)): no while a save is presented, the original's answer while the cartridge slot is (`Saves::card_missing`); in the list's listener for the entry at the cursor, before the select entry runs. A save of the same game behind a cartridge is never presented in the cartridge's place. Every read that starts clears the signal, a save's included, so `Saves` keeps a removal it was told of until the next scan.
- **The list is always built to the end.** Before each read the list-next entry asks the same, and skips a cartridge whose card is gone without reading it: it gets no entry, and every save is still read. The site is also reached in state 1, when the first item's card is gone (`00244F00`); the entry then skips that item the same way, where the original went on to the Virtual Console titles.

The list holds 40 entries: 40 kind bytes at `task + 0x3C` up to the count at `+0x64`, and 40 info entries of 0x24 bytes at `[task + 0x38] + 0x90`, ending before the fields at `+0x630`. The original does not check that bound; it cannot exceed it with one cartridge and 39 Virtual Console titles. The patch builds the list with the original's loop unchanged, and adds a save on the SD card only while the list has room for it (`LIST_LIMIT` in [cart.rs](../patches/transporter/src/cart.rs)): with one language listed there are at most 11 entries (one per DS game, where the cartridge stands in for the save of its own game, and seven titles). A host test holds that for the payload's copy of the titles' languages (`one_language_never_fills_the_game_list`), and the builder compares that copy with the table in the executable (`002AFE0C`) and refuses to build if one language could fill the list. The redirect is based on zaksabeast's DreamRadarCartRedirect, which replaces the same three functions for one hard-coded file.

### Language screen

**Nothing is saved by the original.** Its exheader declares no save data and no extdata. At start, `001058E8` reads the console's language (`001E49BC`, config block `000A0002`), maps it with `00106EAC` and stores it in the byte at `[0032938C]`, which `001E356C` returns. The only other caller of the setter `0022AF28` (`00240D9C`) passes a start-up parameter. Language ids: 1 Japanese, 2 English, 3 French, 4 Italian, 5 German, 7 Spanish, 8 Korean, 9 and 10 Chinese; consoles in Dutch, Portuguese or Russian get 2.

**States.** `get_next_state` (`00242BA0`) and the task factory (`0019CEE4`): 2 is the start screen, 1 the language screen (task vtable `002E6680`), `0x11` a reload that returns to the start screen, 8 the game list. The start screen's outcome `0x12` leads to state 1.

**The screen** (constructor `0022BD28`, vtable `002E543C`, `0xC0` bytes):

| Offset | Content |
| --- | --- |
| `+0x10`, `+0x5C` | Button manager, layout |
| `+0x7C`, `+0x7D` | Part (0 list, 1 kana/kanji, 2 confirm, 3 end) and its step |
| `+0x80` | List index of the picked entry |
| `+0x84` | Kana (0) or kanji (1) |
| `+0x88` | Nine list indices in display order |
| `+0xAC`, `+0xB0`, `+0xB4` | First and one-past-last position of the cursor's range, cursor |

- List index to language id, table `002CA380`: `2, 7, 3, 5, 4, 1, 8, 9, 10`. Buttons 0..8 are the languages in that order, 9 and `0xA` kana and kanji, `0xC` confirm, `0xB` and `0xD` back (button handler `0025BBD8`).
- `0022BC0C` builds the display order, the current language first and the others in table order, and places the nine panes 26 units apart, from 104 down to -104, through `001A1B3C(layout, 1, pane, &xyz)`; the panes of the list indices are in table `002CA3A4`.
- `001A1FE0` sets the cursor's range for the part about to be shown and enables exactly the buttons whose ids are in it (`0022CA5C(buttons, id, 0)`, the others `0022CB98(buttons, id)`). `001A18CC(buttons, id, sound)` gives a button its sound; `0x5000A` is the cancel sound.
- The key handler `0022B330` moves the cursor, presses the button under it on A (`001A2304(buttons, id)`), and on B presses the Back button of part 1 or 2.
- A pressed list button stores its list index in `+0x80` (button listener `0025BBD8`). After the list has faded out, `0022B6DC`..`0022B6F8` send list index 5 (Japanese) to part 1 and every other to part 2. The text frame of the picked language comes from table `002CA70C`; index 5 has frame 0.
- Part 3 calls the task's listener `0025C5BC(listener, language id of +0x80, kanji)`, which switches the language (`0022AF28`), records it in `[manager + 0x168]` (`0022C06C`) and ends the task.

**The patch** ([language.rs](../patches/transporter/src/language.rs)) keeps one byte: the chosen language id, 0 until a choice is made. The listed language is that byte or, while it is 0, the language of the screens; ids without source games become 2.

- The language-chosen entry stores the id instead of switching, if it is a language games exist in. The record in the manager is left alone, so everything else keeps seeing the language of the screens. The reload state still runs.
- **The list.** The language-order entry stands in for `0022BC0C`: the six languages other than the listed one in table order, then list index 7 as the Back button, centred and 32 units apart (96 down to -96), the distance of the long buttons in Bank's main menu (`Turtle_lower5.bclyt` in Bank: 58 down to -102), which the original's nine entries, 26 apart and overlapping, have no room for; the listed language and list index 8 follow and are placed far off the screen. The language-buttons entry runs the original `001A1FE0` and then ends the cursor's range after the shown entries and disables the buttons of the others.
- **Back.** List index 7 is sent to part 3 instead of a sub-screen, so the screen ends as after a confirm; the listener then reports language id 9, which the language-chosen entry ignores. Button 7 gets the cancel sound, and B on the list presses it.
- **Back's text.** The language screen's own message file (36 of the text archive; 24 is the game-selection screen's) has no "Back": its two Back buttons say "Select language" (message 6). The game-selection screen's Back is message `0x1F` of file `0x18` (`002427BC`). The language-order entry opens that file the way `0022EF30` opens a screen's own (`001E6360(0x28, heap)`, `001DFB00(memory, 001E2540(10), file, heap, 1, 5)`, heap from the constructor's parameter `+4`), sets the pane's text with the original's `0019F7B0(strings, layout, pane, messages, message)`, which copies the string, and deletes the object through its second virtual function, as `0022F004` does.
- **The Back button's panes** ([lytpatch.rs](../patches/transporter/src/lytpatch.rs)). The language screen is one of Bank's screens, and the Back buttons of Bank's menus (`Turtle_lower5.bclyt` in Bank, panes `5`, `l`, `2h`) are a 304x30 long button holding a text pane centred at (0, 0) and a 30x30 `return_icon.bclim` at x 137, drawn as the texture is: teal, `008899` (material black colour 0, white corner colours). The game-selection screen's Back (`Salmon_lower4.bclyt`, pane `3`) is the same in Transporter's brown: its material's black colour `FFFFFF` turns the icon white and the pane's corner colours tint it `533324`, a brown near the dark end of the button's bar (`482321` to `7C3C2F`) but none of its pixels. The language screen's layout (`Turtle_lang_select_lower.bclyt`, 12,680 bytes; pane names are the pane ids in base 36) has the same long button in blue for each list entry, but with the language's name as a picture. The layout check sees every layout binary before `Layout::Build` (`0013AEF8`); the payload gets the ones of this size and changes exactly this one, identified by its CRC-32: the picture `1a` of the Simplified Chinese button `m` becomes the icon (the texture name it refers to is replaced by `return_icon.bclim`, which the common archive `a/0/4/5` holds and this screen loads; size and position as in Bank; the material's black colour, `323232` for the name pictures, becomes 0 as in Bank's icon material, so the icon has the texture's teal), and the text pane `2e` of the kana/kanji part is moved into `m` and centred. The button itself, `m` with `long_button.bclim`, is not changed. A layout is a flat list of sections in which `pas1`/`pae1` bracket a pane's children and nothing refers to a section by offset, so the pane is moved by rotating bytes; no animation of the screen names the moved or changed panes. If the layout is not the known one, it is left alone: the entry keeps its Chinese picture and still works as Back.
- **Virtual Console titles.** The scanner (`0024120C`) walks the table `002AFE0C`, 39 rows of `{ version, language id, title index }`, and gives row `i` the list kind `i + 5`. For each installed title, number `j` in the order found, it writes the kind to `scanner + 0x30 + j` and the trainer's name and ID to entry `base + j` of the list's info table (`[task + 0x38] + 0x90`, 0x24 bytes each: name 0x1A, ID at `+0x1C`), where `base` (`scanner + 0x5A`) is the number of entries before the titles. The game list appends the kinds in the loop `00245064`..`00245094`. Kinds and info only stay in step if every found title is listed, so the titles of other languages are left out where they are found: the title-scan entry replaces the scanner's question `002512A8(version, language)` (`002412D4`, its only caller) and answers no for them. Leaving them out in the list loop instead would show each later title with the name and ID of its predecessor, while the game opened would still be the right one, since confirming reads version and language from the table by the kind (`002448C0`, `0024492C`).
- **Their saves.** The scan `001E419C`, which the search (step 2) and the list's scanner (`0024120C`) run, mounts the save of each of the 39 titles as `datv:` and notes in `003296E4[i]` whether it opens; the language of title `i` is `002C2B1C[i]` (`language::VC_TITLE_LANGUAGES`, compared by the builder). Only the search's `00251304` and the scanner's `002512A8` read that table, each right after the scan. Application init's scan (`0010621C`, before the payload can run) is skipped, since nothing reads its result. The mount stub (`001E41C0`) skips the titles in another language than the listed one: no mount, no unmount, their entry stays as the scan cleared it. In German 6 of the 39 saves are looked at, on the main thread at the search. Titles of another language therefore no longer count as found at the search either; the list would not have listed them.
- **Gen 5.** The scan for SD saves and the cartridge use the letter of the listed language ([Saves on the SD card](#saves-on-the-sd-card)).

**The start screen.** The start prompt and the logo are pictures (`push_start_button.bclim` in the lower layout `Salmon_lower3`, `Salmon_logo.bclim` in the upper one), both in archive `a/0/4/6`, whose one entry exists in a variant per language id (0 the default, used for Japanese; 2, 3, 4, 5, 7, 8, 9, 10). Japanese, English and Korean have the same prompt; the logo differs in all. An archive entry is read in the variant of the global at `002F4D7C` (`001DDC0C`), which the original sets through `001071B0` to the language of the screens whenever that changes (`00104EBC`, its only caller). The start screen's constructor (`0024B9E4`) loads its three archives (`0x2C`, `0x2D`, `0x2E`) and builds its layouts in one call (`0024BA70`); the title is built anew each time the language screen ends. The two entries call `001071B0` around that call: with the chosen language before it, if one was chosen, and with the language of the screens after it. The other two archives have one variant only, and the screen's texts come from the text archive of the screens' language, which that global does not touch.

**A console set to Chinese.** The screens are in Chinese (ids 9 and 10), the listed language is English until one is chosen, so English is the hidden entry. The Chinese entries are never offered as languages: list index 7 is the Back button, index 8 is hidden. Back reports id 9, which is ignored whatever the screens' language is. All ten text archives, both Chinese ones included, have message `0x1F` in file `0x18`.
